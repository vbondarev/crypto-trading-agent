## 1. Цель и жёсткие границы

Создать специализированные инструкции в `.agents/skills/*/SKILL.md`, которые **по запросу** помогают ChatGPT последовательно выполнять аналитические задачи MVP: проверка источников и их актуальности, рыночный/технический анализ, разбор полного фьючерсного портфеля, риск-менеджмент, выбор торговой стратегии, подготовка конфигурации **одной выбранной** платформы Veles/GinArea и повторный аудит. Skills ссылаются на утверждённые первичные документы и **не копируют** тысячи строк методик; глобальные ограничения остаются в [AGENTS.md](../AGENTS.md) и [сквозных правилах](agent-operating-rules.md).

**Стратегическая развязка:** этап 07 = **сами специализированные Skills и контракты их вызова/проверки**, этап 08 = **фиксированные пользовательские промпты, workflows и шаблоны отчётов**, этап 09 = **независимые обезличенные испытания**, этап 10 = **разбор TREEUSDT/Veles**. Подготовка Skills **не равна** их реальному автоматическому обнаружению ChatGPT при наличии GitHub-ссылки; чтение конкретного файла/ветки нужно подтвердить в действительной среде.

**Только документальный MVP:** не создавать Bybit API-клиент, самостоятельный торговый движок, инструменты постановки заявок, задачи автономного мониторинга или доступ к приватным API-ключам. Реальные снимки портфеля/форм и результаты разборов остаются в чате, **не в публичном GitHub**. Обезличенные тесты — с полностью вымышленными значениями, без предположений о текущем рынке. Отсутствующие инструменты/подключения → явное ограничение, не фиктивный «тест API». Никаких реальных сделок и гарантированной прибыли.

## 2. Основания, формат и загрузка

**Уже утверждено:** [AD-001…AD-009](architecture-decisions.md) (особенно назначение `.agents/skills/*/SKILL.md` в §3, работа с GitHub, приватность и AD-009), [MVP](mvp-scope.md), [FR-001–FR-053](requirements.md), [AGENTS.md](../AGENTS.md), [T01–T06](input-templates.md), [источники и доступ](data-sources.md), [проверка данных](data-validation.md), [актуальность](data-freshness.md), [анализ риска](risk-management.md), [результаты 06](stage-06-review.md), [Veles](platforms/veles.md), [GinArea](platforms/ginarea.md), [контракт конфигураций](platforms/configuration-contract.md).

**Публичные документы формата, просмотрены 16.10.2026:**
- [Agent Skills Specification — agentskills.io](https://agentskills.io/specification): каталог `skill-name/SKILL.md`, обязательные YAML `name` и `description`; название — lower-case kebab-case, совпадает с каталогом, **≤64 символа**, непустое описание **≤1024 символов**; `references/` и `assets/` — необязательные ресурсы. Инструкции Markdown после frontmatter; ссылки относительно папки skill.
- [OpenAI API — Skills](https://developers.openai.com/api/docs/guides/tools-skills): формат поддерживается в отдельных совместимых средах, но **не доказывает**, что обычный диалог ChatGPT автоматически загрузит Skills из публичного GitHub.

**Формат базового SKILL.md, пока лишь образец (не создан на этапе планирования):**

```yaml
---
name: data-verification
description: Use when checking freshness, provenance and market/account data before crypto analysis or a bot configuration.
---
```

Далее — короткие исполнимые инструкции: `When to use`, `Inputs`, `Do`, `Must not`, `Outputs/status`, `Evidence & freshness`, `Read references`, `Synthetic checks`. Детали ссылать на утверждённые `docs/` через проверенные относительные пути **от каталога Skill**; `references/` создавать только для удобных локальных справок, без несогласованных копий. Каждому Skill дать **положительные и отрицательные** триггеры: какие запросы обслуживает и когда его не запускать.

**Требования к воспроизводимости:** зафиксировать `repo+branch+commit`, фактический способ чтения, доступность, объём фактически полученного контекста и ссылку на источник. `SKILL.md` в GitHub не предполагается автоматически установленным или автоматически прочитанным ChatGPT. Если внешний движок загружает Skills, подтверждать это отдельным тестом среды; если нет — явно просить пользователя запустить поддерживаемый способ чтения.

## 5. Общие критерии для каждого Skill

1. **Назначение и загрузка:** корректный `SKILL.md` с валидным YAML `name/description`, однозначный триггер, ограничения, ссылки на действительную инструкционную ветку/commit; не утверждать автообнаружение.
2. **Область:** только Bybit USDT perpetual для критичных конфигураций, выбранная пользователем платформа Veles или GinArea; иная биржа/рынок/неподдержанная стратегия → отдельная проверка, не перенос настроек.
3. **Приоритет:** системные ограничения > пользовательские согласованные жёсткие лимиты > `AGENTS.md`/утверждённые нормы > специализированная инструкция > локальные примеры; при конфликте `UNVERIFIED`, не молча изменять risk-gate.
4. **Факты:** P01 официальная справка, P02 актуальная пользовательская форма, T02 актуальная полная биржевая экспозиция, Mark с источником и временем. Нет ключа/данных — явно `NEEDS_DATA` или `UNVERIFIED`, не выдумывать API.
5. **Риски:** FR-029 ≤30% Equity маржа; FR-030 loss bound ≤5% Equity; FR-031 ≤5×; FR-032 ≥15% adverse Mark до надёжно оцененной ликвидации; FR-033 ≤3 потенциально активных биржевых слота; FR-034 резерв полного набора возможных IN; FR-038 F/A/H/R, FR-040 no false `READY`.
6. **Позиции/ордеры:** текущие и будущие IN/OUT, partial fills, account/symbol/positionIdx/orderId, чужие боты, owner, ручное вмешательство, Funding/fees/H01. `FILLED` IN не считать заново будущим ордером, **будущие IN на новой паре учитывать в прогнозе FR-033** — регрессия 06.8.
7. **Неподтверждённые защиты:** RV-02 Cross UTA MMR, RV-03 Short worst loss, RV-04 реальные поля, RV-06 независимое исполнение, TV-01–TV-04 и реальное F/A/H/R **остаются блокирующими там, где применимы**. Отсутствие только H02/H03 истории Equity → `NOT_CHECKED`, не hard fail; доказанный H04 запрещает новый риск.
8. **Выходы и безопасность:** пользовательские `READY/NEEDS_DATA/UNVERIFIED/REJECTED` по утверждённому контракту, а `NOT_CHECKED` и `LOCAL_PASS_NOT_READY` — лишь внутренние диагностические метки. Никакой Skill не выставляет ордера, не сохраняет личные ключи, не утверждает, что отслеживает рынок между запросами.
9. **Проверки:** по каждому Skill — ясные acceptance criteria, несколько позитивных и негативных синтетических случаев; фактически выполненные тесты считать отдельно от документальных сценариев, независимый ChatGPT тест заявлять только при подтверждённом отдельном запуске.
10. **Эволюция:** изменение библиотек/справочников 04–06 не скрывать; при конфликте отслеживать точный документ/версию и согласовывать корректировки. Не переписывать ранее принятые ограничения ради прохождения тестов.
