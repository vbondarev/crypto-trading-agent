## 1. Назначение и точная граница

**Цель:** по явному выбору пользователем **Veles** и его конкретной торговой идеи провести от намерения к **черновику R2** либо к **проверке R3** только **действительно видимых полей P02** Veles, без автоподстановки GinArea и несуществующих контролов. До пользовательского выбора платформы — сравнение в `CHOOSE`, не конфигурация Veles. Принятие *шага проекта* 08.6 **не** означает выбор Veles для реальной сделки.

**Нормативный порядок:**
1. `CHOOSE`: пользователь явно выбирает **Veles**; затем конкретные **SIMPLE / CUSTOM / SIGNAL**, `Long/Short`, Bybit `USDT Perpetual`, пару, цель `new_bot|edit_bot|running_trade|takeover|recovery`. Не переопределять заявленное. Названия UI `Тип торговли` (Long/Short), `Режим торговли` («Простой»/«Свой»/«Сигнал») и `Тип маржи` (Cross/Isolated) — разные понятия; Hedge/One-Way — реальная настройка биржевого account, не гарантированное поле формы.
2. `P01`: читать действующую официальную справку/принятые `VL-01–VL-25`, сохранять source URL/date/version/scope; эти сведения **не удостоверяют** наличие/границы поля в конкретной P02. Не считать выбранную биржевую пару доступной именно в Veles без факта из пользовательского селектора.
3. `P02`: для **один-в-один точной таблицы** проверить пользователем предоставленный фактический экран/вкладки `new/edit/active` со `snapshot_at, version_or_UNKNOWN, label, visibility, unit, selected_value, allowed_options, min/max/step, selected_connection, symbol, strategy`. Даже достоверный P02 screenshot — пользовательский материал, не независимый API. Нет P02 ⇒ **только R2 документальный черновик** с `UNKNOWN` вместо точных UI значений; **нет финального copy-ready R3**.
4. `T02/T03/T04`: при позиции, усреднении, Cross или финальном допуске учитывать **весь** фьючерсный портфель Bybit: Equity, S0 текущие позиции/IM/MM, S1 биржевые заявки с `leavesQty`, S2 все reachable **PLACED / CONDITIONAL / VIRTUAL / PLANNED IN**, ручные позиции, сторонние боты и их владельцы, S3 стресс. Одно значение «Депозит» Veles не равно `E0`, доступному collateral, IM, максимальному убытку или размеру **первого** ордера.
5. `R3`: непосредственно перед выводом повторно проверить T02 **≤5 минут**, реальный Bybit Mark **≤2 минут**, actual P02 и все AD-009 события; `FR-029≤30% Equity IM, FR-030≤5% proven bot worst net loss, FR-031≤5×, FR-032≥15% verified Mark→liq, FR-033≤3 reachable slots, FR-034 100% future averaging IM+fees/funding/slippage`, H04/day loss/HWM, FR-037 concentration и **реальные Bybit Mark F/A/H/R**. Доказанное нарушение/активный H04 ⇒ `REJECTED`; критичная неподтверждённая Cross/Short/owner/история ⇒ `UNVERIFIED`; отсутствует вход T02/P02/Mark ⇒ `NEEDS_DATA`. Обязательно перечислять сопутствующие неизвестные. **Не выдавать `READY` на основании P01, локальных PASS, stop-price или одного liqPrice**.

Не просить секрет API; существующий `API-ключ (Привязка)` — **селектор заранее установленного подключения**, идентификатор/значение ключа в публичный репозиторий не копировать. Личные скриншоты только в чате, не GitHub.

## 2. Шесть коротких промптов Veles

### P08-24 — выбор Veles и документальный черновик

> Я выбираю Veles для {SYMBOL} Bybit USDT Perpetual, направление {Long/Short}, режим {Простой/Свой/Сигнал}. Подготовь предварительный R2-план только по документированным настройкам Veles, укажи поля, для которых нужна моя фактическая P02. Никаких выдуманных значений, готовности или запуска бота.

**RT07 R2:** если пользователь ещё не выбрал стратегию, уточнить **только** её; не выбирать автоматически SIMPLE. Не требовать полного приватного T02 для простого ознакомительного обзора полей без позиции/риска.

### P08-25 — Veles SIMPLE и полная сетка

> Для выбранного Veles «Простой» {SYMBOL} посмотри Депозит, Плечо, Перекрытие изменения цены, Сетка ордеров, % Мартингейла, Отступ первого ордера, Логарифмическое распределение, Частичное выставление и Подтяжка. По фактической P02 покажи единицы и применимость. Все будущие IN считай обязательствами, включая пока не размещённые. Это только расчётный черновик.

**RT07 R2:** параметры `VL-05/07/11–17` независимы. `% Мартингейла` не GinArea `Мультипликатор`; `Депозит×Плечо` — лишь приблизительный общий номинал, **не** первый ордер или доказанный риск. При `3 CREATED + 7 WAITING` full future сетка включает **все 10 плановых IN**, нельзя резервировать только 3. Алгоритм цены/rounding/tick/qty, реальный биржевой список заявок — проверить, не выдумывать.

### P08-26 — Veles CUSTOM/SIGNAL с отличающимися единицами

> Подготовь сравнение настроек выбранного мною Veles «Свой» или «Сигнал» для {SYMBOL}. В «Свой» проверь базу и единицы каждого IN/TP; в «Сигнал» — подтверждённые индикаторы, таймфрейм, минимальный отступ и условия. Не превращай процент объёма в USDT и не обещай цену исполнения сигнала.

**RT07 R2:** для `CUSTOM` `Объём 30%` без базы ⇒ `UNVERIFIED`, а не `30 USDT`. Для `SIGNAL` offset/trigger не фиксированная цена; совместимость `Cross/Isolated` и конкретной пары/режима требует P01/P02. Не переносить формулу SIMPLE в CUSTOM/SIGNAL.

### P08-27 — Veles TP, SL, BE и фактический момент защиты

> Проверь в Veles для моей выбранной сделки варианты TP, многоуровневого TP, BE и SL. Отдельно покажи, **когда** Veles должен поставить защитный ордер, что реально видно в Bybit и что может не исполниться. Не считай SL гарантированным максимальным убытком Short.

**RT07 R2 → RT09/R3 только по отдельному запросу:** обычный процентный Veles SL по справке ставится **только после последнего IN**, до полного заполнения сетки он может **не существовать на бирже**. SL по сигналу имеет иную семантику базы и может действовать раньше, если P02 подтверждает. TP пересоздаётся при изменении средней, partial TP/BE зависят от фактических исполнений; BE ≠ нулевая чистая H01 после fees/funding/slippage. TP trailing на Bybit `NOT_VERIFIED` без подтверждения конкретной P02/support. `trigger ≠ accepted order ≠ fill ≠ closed position`.

### P08-28 — действующая Veles сделка / POSITION −1 / Stop vs Cancel

> Проверь действующую сделку Veles {SYMBOL} и соответствующую Bybit позицию. Если включено «Включать позицию на бирже в сделку», посчитай POSITION −1 ровно один раз. Раздели «Остановить», «Отменить сделку», «Закрыть по рынку», «Ошибка» и «Перезапустить» по фактическим биржевым последствиям. Никаких действий самостоятельно.

**RT07 + RT04/RT10:** `POSITION -1` — **виртуальный** учёт уже существующей позиции, **не новый exchange IN/slot/orderId**. `Отменить сделку` может снять управление/заявки бота, но фьючерсная позиция **остаётся открытой**; проверять Bybit `positionIdx/orderIds`, confirmed cancellations/fills. `Остановить` может ждать завершения сделки; `Закрыть по рынку` — намерение, не подтверждение fill; `Restart` создаёт новую reachable IN-нагрузку и требует `RECHECK`. Не считать изменение редактора следующей сделки изменением текущей.

### P08-29 — финальная сверка выбранной формы Veles

> Я выбрал Veles, {SYMBOL}, {Long/Short}, {SIMPLE/CUSTOM/SIGNAL}. Проверь мою актуальную фактическую P02 и свежий полный Bybit T02/T03/T04 перед ручной настройкой. Составь таблицу «поле именно моего интерфейса → значение → единица → источник/время → риск», отдельно перечисли S0–S3 и все FR-гейты. При отсутствии доказательств не ставь READY.

**RT09 R3:** таблица только из **реальной текущей P02**, подтверждённых `Bybit instruments-info` фильтров и актуального целого portfolio/Mark. При открытом блокере — назвать `REJECTED/UNVERIFIED/NEEDS_DATA` с причинами и не подменять это копируемой финальной формой. **Пользователь сам** применяет настройки, агент не нажимает «Создать / Обновить бота».

## 4. R3 guard и AD-009

Синхронное обновление `T02 (≤5m)` + `actual Bybit Mark (≤2m)` + `P02` и всех S0–S3 **перед финальным утверждением**, включая любой fill/partial fill, новые/отменённые заявки, изменение бота/сетки, Equity, margin/leverage/mode, `POSITION -1`, restart. Даже если time TTL не истёк, событие сбрасывает старый риск-вывод ⇒ `RT10 RECHECK`. Недостоверный источник, Binance Spot вместо Bybit Mark и HTTP403 прямого API **не** подтверждают биржевое наблюдение.

**Открытые TV-01–TV-04** сохраняют ограничения подтверждения происхождения/качества данных и конфликтов источников. Цена **Last** — цена последней сделки, **Mark** — отдельная биржевая метрика; Last/Binance Spot не заменяют Bybit Mark в проверке ликвидационного расстояния.

Risk hard gates **FR-027–FR-040**: IM ≤30% Equity, доказанная bot worst net loss ≤5%, leverage ≤5×, проверенная неблагоприятная Mark→liq distance ≥15% (Cross account-wide MMR обязателен), ≤3 одновременно достижимых exchange position slots, полный резерв **100%** будущей маржи + fees/funding/slippage, подтверждённые Moscow day loss ≥3% или HWM DD ≥15% / active H04 блокируют новый риск; F/A/H/**real historical Bybit Mark**/R нужны все. H02/H03 без достоверной истории => `NOT_CHECKED`, не ноль риска, известный H04 => `REJECTED` при увеличении экспозиции. Положительные проверки по отдельности **не гарантируют READY**.
