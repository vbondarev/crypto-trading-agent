# Протокол проверки доступа к данным — этап 04.3

> **Статус: ШАГ 04.3 ЗАВЕРШЁН И УТВЕРЖДЁН ПОЛЬЗОВАТЕЛЕМ (14.10.2026).** Испытаны 20 исходных групп источников, 12 альтернативных маршрутов, синтетический ввод, пользовательское изображение, предоставленные ответы Bybit Kline/Tickers/Instruments Info/Risk Limit и отказоустойчивость X/TG и других каналов (§7–§14). **Утверждены результаты и ограничения исследования**, а не работоспособность всех источников: прямой X и Bybit API остались недоступными, полнота данных/личного портфеля не подтверждена, текущие торговые конфигурации не признаны `READY`. Сведения пользователя и сырые котировки не публикуются. **Исторические пометки «04.3 открыт» в промежуточных протоколах ниже отражают состояние на дату отдельных испытаний; окончательное решение — §15.** Этап 04 продолжается с 04.4 **только после отдельного начала работ**.

Основание: [согласованная матрица, каталог из 20 групп](data-sources.md), [план этапа 04](stage-04-plan.md), FR-007–FR-011, FR-018, FR-026, FR-028, FR-035, FR-040, FR-050 и FR-052.

## 1. Методика и критерии

- **Среда:** веб-поиск и чтение открытых URL в ChatGPT, без отдельного исполняемого HTTP-клиента, собственного сервера, API-ключей, авторизации, подписок и фонового мониторинга.
- **Дата испытаний:** **2026-10-14**; время в минутах/секундах для каждого запроса не фиксировалось надёжным журналом и **не выдумывается**. Время чтения страницы **не считается** временем биржевого наблюдения значения. Этим тестом **не устанавливаются** сроки свежести RV-05.
- **Контрольный инструмент:** `BTCUSDT`, **Bybit USDT Perpetual**, запрашиваемая категория `linear`. Тестовый инструмент не означает чтение реальных позиций пользователя. Для свечей тестировался `interval=60` (`1h`) и `limit=5`; остальные 15m/4h/1d **не подтверждены**, когда базовый endpoint не дал данные.
- **`VERIFIED_ACCESS`** — в этой сессии удалось прочесть **реальное** значение нужной категории вместе с достаточной информацией о его предмете, периоде/времени для соответствующего типа данных. **Указывается область подтверждения**, не весь источник.
- **`PARTIAL`** — страница/часть данных читается, но отсутствуют ключевые поля, точная дата, совпадение инструмента/рынка, числовой график или гарантии пригодности для исходной задачи.
- **`UNAVAILABLE`** — прямой тест указанных данных не дал их прочитать (включая HTTP 403/451, ошибку инструментов, пустую динамическую страницу); **не означает**, что сервис глобально не работает или у других пользователей нет доступа.
- **`NOT_TESTED`** — не было фактического теста соответствующего потока (авторизованные личные данные, скриншоты, конкретный токен-проект, все платные API).
- **`DOCUMENTED`** — подтверждено существование API/формата **из документации**, но **не** фактическое получение значений; эта пометка независима от четырёх статусов теста.

Если отдельные значения страницы отображаются как «today», «recently» или приблизительный относительный возраст, это **не полноценный timestamp** биржевой котировки. **Примеры ответа внутри документации API являются схемами, а не наблюдаемыми значениями рынка.**

## 5. Рекомендации для дальнейших шагов, без подмены решения

1. **Не объявлять `READY` при отсутствии проверенной биржевой Mark Price**, полной проверки счёта и расчётной модели ликвидации. Без них допускается только справочный/предварительный сценарий или запрос данных. Привычный вид торговой страницы и поисковые фрагменты **не заменяют** текущие данные.
2. **Прежде чем признавать решение о бесплатном автоматическом получении биржевых данных состоятельным**, нужно проверить альтернативные допустимые пути на 04.4/04.5 либо предложить пользователю **предоставлять свежие значения/выгрузки** для конкретной задачи. Источник может работать в ином браузерном окружении; этот результат не доказывает техническую невозможность доступа вообще.
3. **Формализовать RV-05 на 04.4:** различать `observed_at`, `published_at`, `retrieved_at` и `snapshot_at`; установить правила для цен, свечей, отчётов, соцпубликаций, динамической карты, личного портфеля.
4. **Проверить работу с пользовательскими материалами на 04.5/04.7:** синтетический текстовый снимок, скриншоты и выгрузки с соответствующими метками. Пока **не объявлять** успешным OCR/парсинг реальных файлов или реальный доступ к Bybit.
5. **Не выдавать выдачу поисковой системы за содержимое источника:** если поисковик показывает недавний заголовок, агент может сослаться на него с ограничением, но не утверждать, что просмотрел первичную статью и проверил её числа.
6. **Сохранить решение RV-01:** исторический HWM/дневная база необязательны; отсутствие полной истории Equity `NOT_CHECKED` не блокирует `READY` **само по себе**, однако это не ослабляет проверку текущего риска.

### 10.3. Правила воспроизводимого расчёта

- Привести семь полей каждой свечи к соответствующим числовым типам, отсортировать по `startTime` по возрастанию. **Не** рассчитывать индикаторы на исходном обратном порядке массива.
- Закрытая часовая свеча: `startTime + 3 600 000 ≤ response.time`. Для данной записи последняя закрытая свеча открылась **2026-10-14 18:00 UTC**, последняя незакрытая — **19:00 UTC**.
- **EMA(35):** стартовая EMA = SMA первых 35 закрытых `close`, затем `alpha=2/(35+1)` и рекуррентная EMA по последующим закрытиям.
- **RSI(14) (Wilder):** начальные средние прирост и убыток по первым 14 изменениям close; далее сглаживать с множителем `1/14`, использовать раздельные положительные и отрицательные изменения.
- **ATR(14) (Wilder):** `TR=max(high-low, |high-prevClose|, |low-prevClose|)`; для самого первого бара `TR=high-low`. Начальная ATR — SMA первых 14 TR, далее сглаживание Уайлдера `1/14`.
- Отличие от TradingView/другого терминала возможно из-за **seed/прогрева**, трактовки незавершённого часа, начальных баров и типа свечной цены; сравнение с внешней эталонной реализацией в этом тесте **не выполнялось**.
- 199 последовательных закрытых часовых баров достаточно для этих **конкретных** индикаторов с указанной инициализацией; они **не заменяют** требуемые 15m/4h/1d, историю уровня Mark, OI/funding, риск-проверку и расширенный исторический стресс-анализ.

### 13.3. Проверяемая формула и контрольный синтетический пример

[Bybit: Maintenance Margin USDT](https://www.bybit.com/en/help-center/article/Maintenance-Margin-USDT-Contract) приводит:

```text
Position Value = Position Size × Mark Price
Position MM = Position Value × selected-tier MMR − selected-tier mmDeduction

Tier 1: deduction = 0
Tier n: deduction[n] =
  deduction[n-1] + riskLimitValue[n-1] * (MMR[n] − MMR[n-1])
```

**Синтетический пример, не реальная позиция пользователя:** для объёма **1 000 000 USDT** во второй ступени с `MMR=0.005` и `D=510 USDT`:
`MM = 1 000 000 × 0.005 − 510 = 4 490 USDT`.

Это **только компонент поддерживающей маржи самой позиции**, без отдельной маржи на активные ордера, оценочной комиссии закрытия и воздействия прочих позиций Cross; это **не** расчёт ликвидации. Официальные материалы отдельно описывают расчёт MM ордеров и комиссию закрытия.

### 13.4. Как определять ступень и чего недостаёт

Согласно [Bybit: Risk Limit](https://www.bybit.com/en/help-center/article/Risk-Limit-Perpetual-and-Expiry-Contracts):

- Учитываются стоимость действующих позиций и стоимость ордеров, способных **увеличить** позицию. Для USDT linear используются количество и **Mark Price** при расчёте эффективного риска (методика отдельных маржинальных требований к ордерам может отличаться).
- Для One-Way и Hedge требуется корректное разнесение Long и Short по сторонам, а не суммирование заведомо закрывающих ордеров; для эффективной стоимости применяется **максимум** соответствующих нагрузок Long/Short.
- `Reduce Only` и `Close on Trigger` **исключены** из расчёта `Effective Position Value`, но без подтверждения назначения конкретного пользовательского ордера исключать его из общего риска нельзя.
- Risk tiers зависят от стоимости на Mark Price; увеличение количества/цены может изменить ступень, ставки маржи и допуск новых ордеров.
- Стандартные Risk Limit применяются к **Cross** и **Isolated**, а при **Portfolio Margin** используется отдельная портфельная модель; нельзя механически применять эту таблицу как формулу риска Portfolio Margin.

**Критически отсутствует для FR-018–FR-040:** подтверждённый охват счёта, Equity, все реальные позиции/отложенные ордера/боты и их полные IN-сетки, фактические условия режима Cross/Isolated, комиссии/финансирование, корректная модель поддерживающей/начальной маржи с учётом всех позиций и динамической стоимости на Mark Price, цена ликвидации и стресс-тесты. **Нельзя устанавливать `READY`** на основании одного публичного риск-каталога.

### 13.5. Вывод по 04.3

**Подтверждено для резервного маршрута:** пользователем переданы пригодные для структурного анализа ответы Bybit V5 `Kline` (§10), `Tickers` (§11), `Instruments Info` (§12), `Risk Limit` (§13). Распознаны фьючерсный рынок, закрытые свечи, основные котировки, виды OI, funding, минимальные ордера, сетка биржевых ставок маржи, ограничения плеча и рекуррентная формула MMR deduction. Схемы проверены по официальной документации.

**Не подтверждено:** собственный автоматический HTTP-доступ ChatGPT к Bybit, происхождение пользовательских JSON от подлинного API, полнота всего портфеля и реальная текущая Cross/Isolated/Portfolio Margin риск-оценка. Не повышать `BY-R` или `BY-M` до `VERIFIED_ACCESS` **для прямого веб-канала ChatGPT** из-за успеха ручной передачи.

**Шаг 04.3 остаётся ОТКРЫТ.** Дальнейшее расширение ручных тестов публичных API необязательно для доказательства **существования рабочего пользовательского резерва**; можно представить накопленные результаты на согласование и только после явного решения переходить к **04.4 (правила времени/свежести)**. Для последующих этапов также потребуется отдельная полноценная проверка риска пользовательского портфеля.

- **Конкретное сообщение X/TG:** без оригинального текста, надёжной датировки и проверенного автора остаётся `MISSING/UNVERIFIED`, даже если поиск нашёл цитату; отправка пользователем точной ссылки/датированного снимка — **кандидат**, но пользовательские сведения не становятся автоматически независимо подтверждёнными.
- **Настроения X:** без полномасштабной выборки и воспроизводимого периода не выдавать количественные проценты и тренд. В MVP этот канал **не имеет доказанного автоматического резерва**. Подключение сторонних приложений/X API или Work-браузера **не испытано**, платная инфраструктура в текущем MVP не предполагается.
- **Приватные биржевые данные:** нужен датированный полный пользовательский снимок, включая все действующие позиции и будущие сетки. Публичные страницы не доказывают охват/Equity/ликвидацию Cross.
