## 1. Обязательная граница и доказательства

**Цель:** перевести согласованное торговое намерение (направление, зона входа, сценарии усреднений/выходов, обеспечение, стоп, риски) в **только существующие и применимые поля ОДНОЙ выбранной платформы**; связать числовые настройки с реальным портфелем Bybit и отдельной контрольной точкой R3. Не переносить настройки второй платформы даже под похожими названиями.

**Основания в репозитории:** [06.1: P01/P02](platform-validation.md), [06.2–06.3: Veles](veles.md), [06.4–06.5: GinArea](ginarea.md), [этап 05: портфельный риск](../risk-management.md), [свежесть AD-009](../data-freshness.md), [FR-047–FR-053](../requirements.md). Утверждение плана не даёт права обойти FR-027–FR-040.

**Внешние первоисточники, повторно сверены 16.10.2026:** [Veles: общие настройки](https://help.veles.finance/ru/platform/settings/full/), [Veles: режимы](https://help.veles.finance/ru/platform/settings/trading-mode/), [Veles: стоп](https://help.veles.finance/ru/platform/settings/stop-loss/), [GinArea: размеры](https://help.ginarea.org/ru/settings/orderdetails/), [GinArea: сетка](https://help.ginarea.org/ru/settings/gridsettings/), [GinArea: вход и выход](https://help.ginarea.org/ru/settings/positionset/), [GinArea: TP/SL](https://help.ginarea.org/ru/settings/tpslset/), [GinArea: Bybit modes](https://help.ginarea.org/connection/exchangesetup/), [Bybit V5: instruments-info](https://bybit-exchange.github.io/docs/v5/market/instrument), [Bybit V5: place order](https://bybit-exchange.github.io/docs/v5/order/create-order), [Bybit V5: orders](https://bybit-exchange.github.io/docs/v5/order/open-order), [Bybit V5: position](https://bybit-exchange.github.io/docs/v5/position). ### 1.1. Схема входа и артефактов (имена — внутренний контракт, не UI)

| Слой | Обязательные сведения | Причина блокировки |
|---|---|---|

| **P01** | Официальная применимость версии/стратегии/пары/режима и ограничения с source_id/time; incompatibility flags | Запрещён режим, не доказана пара, противоречие справки |

| **MappingTrace** | для каждого поля: intent_metric, canonical_value+unit, P01/P02 evidence, exact_ui_label, normalized_to, conversion, rounding, side_effects, risk_snapshot_ref, status/reason | Вывод не воспроизводим, скрыт значимый эквивалент/неэквивалент |

**Запрет:** Internal field IDs и нормализованные названия — **НЕ** поля платформы. Не включать в финальный «один в один» экран вымышленные label/поля. Если пользователь не предоставил точную P02, можно дать **предварительный расчёт**, но не готовую для копирования/запуска конфигурацию.

### 1.2. Строгий порядок

1. **Выбор пользователя (FR-046/047).** Есть одна явно выбранная платформа и стратегия, а не оба конфига параллельно. Смена платформы — новый запрос/проверка.
2. **Совместимость P01.** Bybit USDT perpetual, реальная пара в селекторе бота, точный UTA/Margin/Position mode, Long/Short, выбранная версия/тариф. По справке GinArea Bybit — UTA/Cross/One-Way, исключение Hedge лишь для Default; Veles position mode проверяется **отдельно**. Несовместимость → REJECTED этой комбинации; неизвестная пара/режим → NEEDS_DATA; конфликт официальных/личных сведений → UNVERIFIED.
3. **Канонизация.** Зафиксировать сторону/слот, currency units, модель цены (Mark/Last/Index/limit/trigger), стратегический бюджет vs фактический collateral и полный список достижимых событий.
4. **Сопоставление только P02.** Использовать exact UI labels, реально подтверждённые вкладки, visible_if, значения/пределы, поля сохранения/редактирования, version. Нет P02 → NEEDS_DATA; спорная семантика → UNVERIFIED.
5. **Bybit-совместимость.** Отдельно вычислить quantity, nominal, биржевые ticks/lot/min/max/status, reduceOnly/closeOnTrigger/triggerBy там, где **действительно доказана** поддержка платформой и моделью. Не выдавать API-поля Bybit за поля пользовательского интерфейса.
6. **Портфельное моделирование.** Учитывать S0→S1→S2→S3, 100% потенциальных будущих усреднений плюс fees/funding/buffers, все других ботов, ручные позиции, владельцев и полные стрессы. Никакой фиктивной гарантии SL/TP.
7. **R3.** Перед окончательным конфигом заново сверить T02 не старше 5 минут и без событий, Mark не старше 2 минут или строже по AD-009, актуальные P02 и инструмент. FR-029≤30% Equity margin, FR-030 доказуемый worst bot loss≤5%, FR-031≤5x, FR-032 запас≥15%, FR-033≤3 позиции и FR-034 полный резерв — без ослабления. H02/H03 без достоверной истории NOT_CHECKED; доказанный H04 блокирует новый риск.
8. **Решение/аудит.** REJECTED — доказанный запрет/нарушение; UNVERIFIED — конфликт/недоказуемая важная модель; NEEDS_DATA — отсутствующий обязательный снимок/поле. READY **только** при истинном выполнении всех обязательных проверок — публичная справка/синтетика сами по себе READY не создают. Записывать provenance и конкретные неизвестные, но без настоящих ключей/приватного портфеля в публичном GitHub.

## 2. Канонические величины и правильные единицы

| Термин | Определение в аналитической модели | Запрет смешения |
|---|---|---|
| **Q_base** | Количество актива/контрактов после доказанной спецификации символа | 20 USDT ≠ 20 SOL/BTC |
| **P_entry / P_mark / P_trigger** | Цена в единицах quote/base, **три разных основания** | Mark ≠ Last; price stop ≠ гарантированная цена исполнения |
| **N_quote** | Условно для линейного контракта с base qty: Q_base × P_quote_per_base | Номинал ≠ депозит ≠ initial margin ≠ Equity |
| **B_bot** | Бюджет/депозит бота с документированной семантикой платформы | Выделенный в UI «депозит» ≠ зарезервированное Cross-обеспечение |
| **L_position** | Реальное биржевое плечо позиции, множитель × | Приближённое N/B не подтверждает фактическое L и MM |
| **IM, MM, E** | Биржевые initial/maintenance margin и Equity, с scope валютой/временем | Разные единицы USD и USDT без FX не эквивалентны |
| **IN_i** | Одно потенциальное/выставленное/частично исполненное усреднение, с order lifecycle | Число уровней ≠ число активных биржевых ордеров |
| **OUT/TP/SL** | Цель/условие/триггер/ордер/исполнение — разные стадии | «Стоп задан» ≠ «защитная заявка активна и исполнится» |
| **Loss_bound** | Доказуемая худшая потеря с gap/slippage, fees и другими достижимыми состояниями | Стоп в процентах ≠ гарантированный предел убытка Short |
| **SeriesPnL (H01)** | Realized/Unrealized PnL согласованной серии с комиссиями/funding | Бот Profit не равен прибыли счёта/серии |

Все математические операции выполняются над **типизированными decimal-значениями**, с отмеченными currency, timeframe, side, version и источником. Никаких неявных приведений USDT→USD, %→fraction или лотов→монеты.

## 3. Матрица отображения: неэквивалентные платформы M01–M24

**Столбцы Veles/GinArea содержат названия из официальной справки, но не удостоверенные поля конкретной P02.** Метки: DOC — документальная функция для указанной стратегии; CONDITIONAL — только когда в P02 доказано; NO_DIRECT_EQUIVALENT — нельзя переносить «один к одному»; UNVERIFIED — недостаточно доказательств.

| ID | Намерение/величина | Veles — документальный способ | GinArea PRO — документальный способ | Инвариант |
|---|---|---|---|---|
| M01 | Биржа и рынок | «API-ключ (Привязка)» определяет Spot/Futures | «Биржа», «Тип бота» USDT Futures | Реально подтвердить Bybit linear и правильную привязку, не публикуя ключ |
| M02 | Пара | «Торговая пара» | «Торговая пара» | Доступность выбранной **стратегии в селекторе**, не только листинг Bybit |
| M03 | Long/Short | «Тип торговли» Long/Short | «Направление торговли» Long/Short или Auto **условно** | Auto ≠ одновременно независимые Hedge-позиции |
| M04 | Режим сетки | «Простой»/«Свой»/«Сигнал» | Default/Auto/Dynamic/Indicator/DCA | **NO_DIRECT_EQUIVALENT**, у каждого свой жизненный цикл |
| M05 | Бюджет | «Депозит»; документально × плечо → номинал сетки | Суммарные IN из «Размер ордера», числа и multiplier; отдельная база под плечо, если подтверждена | **NO_DIRECT_EQUIVALENT**: B_bot Veles ≠ GD-12 GinArea |
| M06 | Первый IN | Veles: доля депозит×плечо / сетка и мартингейл, либо ручной «Свой» | GinArea «Размер ордера» (base/USDT) | Не копировать размер из другой монеты/бота |
| M07 | Максимум IN | Veles распределение/мартингейл; cap одного IN в проверенной базовой форме не доказан | GinArea «Макс. размер» cap отдельного IN | **NO_DIRECT_EQUIVALENT**, cap ≠ total notional |
| M08 | Рост IN | Veles «% Мартингейла» | GinArea «Мультипликатор» | Оба увеличивают размер, но нормировки/% и порядок reset не равны |

| M10 | Число IN | «Сетка ордеров (количество)» | «Количество ордеров», отдельные Long/Short лимиты в нужных стратегиях | Все потенциальные IN; момент выставления отличается |
| M11 | Первый вход | «Отступ первого ордера», режим «Маркет» | IN по сетке/триггеру/индикатору | Не обещать ту же цену, execution и комиссию |

| M13 | Цена/график | Предпросмотр сетки TradingView | Границы/шаг/IN, статистика триггеров | Ни один визуальный элемент не подтверждает реальный orderId |

| M15 | Уже открытая биржевая позиция | «Включать позицию на бирже в сделку»; виртуальный POSITION -1 | Нет доказанного прямого эквивалента безопасного принятия ручной позиции | **NO_DIRECT_EQUIVALENT**; GinArea может Failed при manual Bybit |

| M17 | Несколько выходов | Veles «Свой» мульти-тейки | GinArea OUT-триггеры/объединение, P&L trailing | **NO_DIRECT_EQUIVALENT** по очередности и условиям |

| M19 | Трейлинг | Veles TP trailing не подтверждён для Bybit в перечне справки | GinArea Max Stop/SL trailing/P&L trailing — **разные** опции | Нельзя из одного «трейлинг» создать универсальное поле |
| M20 | Запрет новых IN | В Veles нет подтверждённого поля «Disable IN» с семантикой GinArea | GinArea «Disable IN» + опция вне границ, sticky | **NO_DIRECT_EQUIVALENT**, запрет IN не закрывает позицию |
| M21 | Диапазон | Veles процент перекрытия и подтяжка сетки | GinArea «Границы торгов», Disable latch | Процент coverage не равен абсолютной границе/stop |
| M22 | Остановка/отмена/закрытие | Veles «Остановить»/«Отменить сделку»/«Закрыть по рынку» различаются | GinArea Pause/«Закрыть позицию», TP/SL/stop by time | **NO_DIRECT_EQUIVALENT**: сохраняются позиции/ордера до Bybit confirmation |
| M23 | Режим счёта и плечо | Veles «Тип маржи», «Плечо», Hedge требования отдельной справки | GinArea Bybit UTA/Cross/One-Way, Default может Hedge | UI поле не доказывает смену режима на бирже; лимит 5× независим |
| M24 | Чистая прибыль восстановления | Veles прибыль/бэктест и H01 из фактических fills | GinArea Profit/Realized/Unrealized без полного funding | **NO_DIRECT_EQUIVALENT**; H01 вести отдельно, fee/funding учитывать |

**Ограничение матрицы:** NO_DIRECT_EQUIVALENT означает **не доказано прямое переносимое соответствие**, а не универсальное утверждение «функция никогда не будет реализована»; альтернативу можно предложить как **иной сценарий** после решения пользователя и нового P01/P02. Если поле вовсе не документировано для области применения → **UNVERIFIED**, а не уверенное NOT_SUPPORTED. NOT_SUPPORTED допускается только по явному достоверному ограничению конкретной версии/режима.

## 4. Количество, округление, min/max и сценарные обязательства

### 4.1. Проверка Bybit linear instruments

Получать текущие symbol/status/category=linear/settleCoin и следующие параметры instruments-info: priceFilter.tickSize/minPrice/maxPrice; lotSizeFilter.minOrderQty/qtyStep/minNotionalValue/maxOrderQty/maxMktOrderQty и применимость unified margin. **Не использовать константы из документа вместо настоящих значений по паре**.

1. При **денежном размере IN** в USDT для типового linear base-qty: quantity_exact = nominal_USDT / price_USDT_per_base. Для других контрактных схем требуется проверенный контрактный множитель. Сначала разделить intent USD/USDT/base/quote, затем рассчитать, округлить, проверить.
2. Для **quantity** по шагу qtyStep допустима консервативная модель q_down = floor(q_exact / qtyStep) × qtyStep **в точной десятичной арифметике**; GinArea документально округляет объём вниз. Но это **не универсальное правило округления цены** и **не доказательство**, что каждый Veles/GinArea сценарий сформирует именно q_down.
3. Если q_down < minOrderQty, или q_down × соответствующая цена < minNotionalValue, или превышен maxOrderQty/maxMktOrderQty: **не увеличивать автоматически q до минимума и не уменьшать/перестраивать сетку молча**, так как изменится риск/прибыль. Вернуть нужный статус с объяснением и запросом нового согласования.
4. **Цена:** должен соблюдаться tickSize и диапазон; способ округления зависит от Long/Short, IN/OUT, Limit/Trigger, ограничения нежелательного исполнения и согласия пользователя. Любое округление, изменяющее риск/условие исполнения, требует перерасчёта и может потребовать нового согласования. Не округлять MarkPrice как лимитную цену!
5. **Conditional orders:** Bybit V5 указывает, что некоторые условные заявки не занимают IM **до триггера** и могут быть отменены, если на момент срабатывания обеспечения недостаточно. **По FR-034 резервировать 100% будущих обязательств плюс буферы независимо от текущей занятой биржей IM**; не трактовать условную заявку как гарантированное исполнение.
6. **Bid/Ask и Stop:** Bybit Market ордер может быть IOC-лимитом с защитой от проскальзывания; недостаточная ликвидность → отмена/частичное исполнение. Поэтому нет гарантированной цены/срабатывания/максимума Short-loss только по TP/SL. Mark liquidation отдельно от triggerBy=Last/Index/Mark, если вид триггера подтверждён в P02 и Bybit.
7. **Identity:** ключ только для доказанного (account, symbol, positionIdx, exchangeOrderId); два события одного orderId не удваивают заявку, **два разных orderId по одинаковой цене не схлопываются**; для виртуальных ID без доказанной связи выделять POSSIBLE_DUPLICATE и UNVERIFIED при материальности риска.

### 4.2. Финансовые ограничения до заполнения

**Совокупный риск должен учитывать worst-case доступных состояний**, включая будущие IN GinArea (multiplier, Instop, reset/reopen, потенциальные циклы) и Veles (всю сетку, ожидающие и восстановимые после ошибки уровни), а не лишь нынешний баланс бота. FR-029/030/032/034 проверяются по отдельным позициям и агрегированному T02, с Cross/MMR и слippage/funding. Если нет конечной верхней границы возможных циклов, полного бюджета или worst-case модели → **UNVERIFIED**, а не нулевой резерв. Невозможность подтвердить Cross liquidation RV-02 и Short loss RV-03 нельзя загладить повышенным плечом либо широким SL.

## 5. Полностью вымышленные примеры, не реальные торговые рекомендации

**FX-01 — Veles бюджет не равен первой заявке:** фьючерсный депозит 50 USDT и плечо 3× дают **плановый совокупный номинал примерно 150 USDT** до распределения сетки/доп. действий. В чисто учебном сценарии **пять одинаковых** уровней дали бы 30 USDT номинала на уровень; действительный SIMPLE с мартингейлом может дать другие. **Нельзя скопировать 50 или 150** в GinArea «Размер ордера» по смысловому совпадению «размер».

**FX-02 — GinArea базовый IN vs cap:** условно первый IN=20 USDT (номинал), multiplier=1.5, max=50 USDT, четыре плановых IN: **20 + 30 + 45 + 50 = 145 USDT номинала** до биржевого округления. Резерв и риск считать по **145** и условиям цен/маржи/комиссий, а не по 20 или 50. Это не подтверждённые поля текущей P02 и не рекомендованное плечо.

**FX-03 — quantity и minimum order:** вымышленный symbol с price=2.5 USDT за единицу, IN notional=10 USDT, qtyStep=0.1 base, minOrderQty=1 base, minNotionalValue=5 USDT. Известный линейный base contract даёт qty_exact=4; q_down=4, notional=10, лимиты учебной биржи пройдены. При **вымышленном qtyStep=3**: q_down=3 base, notional=7.5 USDT; при **minNotionalValue=10 USDT** такой ордер не проходит — **не повышать q автоматически**, нужен новый размер/согласование. Эти значения **не реальные Bybit instrument limits**.

**FX-04 — «стоп» не изоморфен:** Veles простому стопу по проценту может предшествовать вся сетка IN; GinArea «Стоп-Лосс» может срабатывать по финансовому результату бота; у GinArea «Мин. Стоп» относится к OUT после ценового триггера. Подстановка «5» в каждое поле не сохраняет ни price trigger, ни величину убытка, ни действие биржи. Без P02 и проверенного результата PnL/price → **UNVERIFIED**.

**FX-05 — действующая позиция:** на Bybit есть ручная Short qty=10 и USDT-PnL серии −15, будущий бот исполнил IN qty=2; фактическая биржевая позиция qty=12 **только при доказанном совпадении слота/стороны**, а не qty=22 из виртуальной отметки. Если затем реализовано +10, списано fee=1 и funding=2, чистый итог серии = **−8 USDT**, а не восстановление. Если другой бот управляет этой парой, ownership остаётся **UNVERIFIED** до сверки.

**FX-06 — цена Mark и риск:** вымышленный Last=102, Mark=100, Binance Spot=108. Значения **нельзя смешивать** с Bybit USDT perpetual как взаимозаменяемые; тип/время/источник определяют пригодность. При отсутствии Bybit T02/Mark для R3 → NEEDS_DATA, даже при идеально переписанной публичной форме.

## 6. Формат ответа пользователю при подготовке конкретной конфигурации

Последовательность вывода:

**(A) Проверенные контексты:** платформа, версия, стратегия, символ, Bybit market, UTA/margin/position mode/side, captured_at, source provenance, независимая проверка; не показывать секреты.

**(B) Проверенные поля выбранной P02:** exact_ui_label, observed_value, proposed_value, unit, allowed_range, exact control, section, visible_if, calc trace, evidence status, user manual action. Любое неподтверждённое поле **не выводить в готовую форму**; перечислить отдельно в «Требуется подтвердить» и дать ссылку на официальный справочник.

**(C) Сценарный расчёт:** IN_i price/qty/nominal, S0/S1/S2/S3, owner, полный IM+fees+funding+buffer, текущее/будущее Equity, 5×/30%/5%/15%/3 slots/100% reserve, стрессы. Для выхода — триггер, ордер, исполнение и конечный net PnL раздельно.

**(D) Решение:** READY / NEEDS_DATA / UNVERIFIED / REJECTED и обоснование, конкретные недостающие данные/риски/источники, ручная проверка сохранённости. Перед началом реальной торговли пользователь **сам применяет** настройки; в MVP агент ничего не отправляет на биржу или в кабинет бота.

**(E) Изменения после записи:** любой fill/partial, новая/отменённая заявка, Stop/TP change, рестарт, Disable IN, смена режима/плеча, manual вмешательство, изменение P02, T02/Mark → invalidate соответствующих расчётов, повторить R3. Исторические H02/H03 без достоверных данных NOT_CHECKED; известное H04 → REJECTED для нового риска.
