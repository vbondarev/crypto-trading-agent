## 1. Область применения, границы доказательности и формат записи

### 1.1. Назначение контракта

Собрать для одной проверки риска **согласованный по источникам, состояниям и времени набор фактов**, из которого следующие шаги смогут оценивать текущий портфель, уже размещённые заявки, условные обязательства и всю планируемую сетку.

- **R1 (обзор):** нужны только входы, требуемые конкретным анализом; приватный T02 не запрашивается автоматически.
- **R2 (предварительная стратегия):** неполные входы позволяют лишь обоснованные условные сценарии; готовность к запуску не заявляется.
- **R3 (финальный допуск):** актуальный **весь** фьючерсный счёт, все позиции, активные/условные ордера, боты и будущие сетки; проверяемая биржевая Mark, биржевые/платформенные ограничения и все применимые риски. Возраст T02 — не более 5 минут и **без изменяющего события**, Mark — не более 2 минут, либо более строгий срок при обстоятельствах из политики свежести. T03/T04 должны относиться к той же непротиворечивой версии состояния. Полнота снимка — отдельный признак, не следствие свежести.

Это текстовый **логический формат для рассуждения агента**, не JSON-схема Bybit API и не обязательная анкета для каждого запроса. Пользователь может прислать скриншот, текст или выгрузку; нормализация не доказывает подлинность, полноту и доступность источника.

### 1.2. Оболочка каждого наблюдения

Каждое числовое или статусное значение хранить вместе со сведениями о происхождении; если одно из критичных полей неизвестно, не конструировать его по контексту.

| Атрибут | Смысл и требование |
|---|---|
| source_id, original_field | Тип канала, происхождение/ссылка или предоставленный файл, **исходное название** поля, идентификатор локального фрагмента без публикации приватных идентификаторов |
| value_raw, value_normalized | Точное исходное представление и отдельно нормализованное **десятичное** значение; не округлять молча, пустую строку и 0 различать |
| unit, basis | Исходная валюта/единица и база оценки; для цены — quote/base, для qty — base/контракт, для денег — USD/USDT/иная единица |
| account_scope, instrument_id | К какому аккаунту/субсчёту/обеспечительному контуру и контракту относится факт |
| observed_at, response_time, snapshot_at, retrieved_at | Самостоятельные временные метки с timezone/UTC-offset; время API-ответа — допустимый оговорённый proxy, время пересылки не делает данные свежими |
| availability, freshness, trust | **Раздельные оси**: доступность канала; состояние по времени; происхождение/непротиворечивость/достаточность |
| required_for, issue | Для какой именно проверки значение обязательно и какой дефект мешает его использовать; ссылаться на FR/ветвь расчёта |

**Классы происхождения значений:** ① биржевое поле, фактически полученное/прочитанное в текущем канале; ② **пользовательский снимок/JSON** с собственным временем и ограничением независимости; ③ явно **вычисленное** из перечисленных входов; ④ явно заданное **допущение** с областью применимости; ⑤ **неизвестно/конфликт**. Официальная документация с примером JSON — **не категория ①**, а только источник описания схемы.

Не смешивать статусы доступности канала (VERIFIED_ACCESS / PARTIAL / UNAVAILABLE / NOT_TESTED), качества полей (CURRENT / STALE / MISSING / TIME_UNVERIFIED / CONFLICT / NOT_CHECKED и пр.) и итоговые торговые статусы (READY / NEEDS_DATA / UNVERIFIED / REJECTED). При известных превышениях использовать приоритет REJECTED, даже если часть входов отсутствует.

### 1.3. Временная целостность и охват

**Ключ версии снимка портфеля:** exchange + account_scope + account_mode + valuation_basis + snapshot_at + coverage_manifest + revision/event_cutoff. Строка account_scope — **локальный обезличенный псевдоним**, не UID/API-ключ. Не объединять несколько счетов, регионов, UTA-контуров либо валют оценки без доказанной единой модели обеспечения. **account_scope** учитывает разделение обеспечительных контуров, не только символ монеты.

- **coverage_manifest**: явно подтверждены охватываемые группы активов, позиции, активные и условные ордера, боты, будущие сетки и необходимые субсчета. Если раздел пуст — подтверждение пустоты обязательно. Отсутствующая страница скриншота **не означает пустой список**.
- **revision/event_cutoff**: последнее известное изменение Equity, ордера, позиции, сетки, режима или критичного рынка после снимка. При изменении затронутая версия считается **STALE_BY_EVENT / INVALIDATED_EVENT**, даже если не истёк TTL.
- Время полей разных снимков можно сопоставлять только при доказуемом общем состоянии и отсутствии значимых событий между ними. Нельзя подменять наблюдение текущего портфеля исторической выгрузкой сделок.
- Если источники одного критичного значения расходятся, ставить **CONFLICT**, указать обе записи и запросить согласование; не усреднять Mark/ликвидацию/маржу, не выбирать удобный вариант.

**Проверенное соответствие отдельных имён Bybit V5 (описание полей, не реальный доступ к счёту):**
- **Wallet Balance**: totalEquity, totalInitialMargin, totalMaintenanceMargin, totalAvailableBalance в ответе UTA документированы в **USD**; ряд агрегатных полей **не применяется к Isolated**, а ограничения и семантика зависят от режима. [Официальный справочник Bybit V5](https://bybit-exchange.github.io/docs/v5/account/wallet-balance).
- **Position Info**: size — неотрицательный размер позиции, side и positionIdx задают сторону/слот; позиционный liqPrice при Cross описан как **оценка**, а пустое значение не равняется цене 0. [Официальный справочник Bybit V5](https://bybit-exchange.github.io/docs/v5/position).
- **Open Orders**: qty, cumExecQty, leavesQty, orderStatus, orderId/orderLinkId, reduceOnly и closeOnTrigger; данные приходят по фильтрам/страницам, а поле cumExecFee для линейных контрактов объявлено устаревшим — использовать проверяемую детализацию при доступности. [Официальный справочник Bybit V5](https://bybit-exchange.github.io/docs/v5/order/open-order).
- **Place Order**: для Perpetual размер **qty**, а не денежный номинал; reduceOnly и closeOnTrigger имеют специальные условия. [Официальный справочник Bybit V5](https://bybit-exchange.github.io/docs/v5/order/create-order).

Эти ссылки описывают **схему на дату ревизии 05.1 (15.10.2026)**. Это не утверждение о самостоятельном доступе ChatGPT к приватному API, полноте ответа, фактическом UTA пользователя или неизменности правил Bybit.

### 2.2. Единицы и допустимые операции

| Величина | Каноническая запись | Пример и правило |
|---|---|---|
| **Цена** | decimal quote/base с точным symbol и типом Last/Mark/Index | 100 **USDT/BTC** и 100 **USD/BTC** — разные денежные единицы; без FX нельзя складывать/сравнивать как эквивалентные |
| **Размер позиции/ордера** | decimal **qty** + base/contract unit + multiplier/тип контракта | **0.2 BTC** — количество базового актива, **20 USDT** — денежный номинал; равенство без цены/спецификации недопустимо |
| **Номинал** | decimal денежная стоимость **в quote**, с видом оценки (Last/Mark/лимитная цена) и временем | Для простого linear-контракта с qty в base: notional_quote = qty_base × price_quote_per_base; при иных контрактных единицах нужен проверенный множитель |
| **Equity, PnL, IM, MM** | decimal + единица валюты и scope | **500 USD Equity** ≠ **500 USDT Equity**; при разной базе требуется проверенный перевод и отметка времени |
| **Кредитное плечо** | множитель **×** без валюты | 5× — не 5%, плечо не заменяет полный расчёт портфельной маржи |
| **Доля** | десятичная дробь (fraction) и явно преобразованный процент | 0.30 fraction = 30%; 0.05 fraction = 5%; 0.0001 fraction = 0.01%, **не 0.0001%** |
| **Funding/fee rate** | fraction за указанный период/событие/сторону + источник | Funding может менять знак; неизвестная ставка **не ноль**. Дневное/8-часовое значение без периода несопоставимо |
| **Время** | ISO 8601 с UTC-offset, плюс тип метки | 12:00+03:00 = 09:00Z; Unix ms нельзя трактовать как Unix sec; UTC-свеча не закрыта по локальным часам |
| **Направление позиции / сделки** | LONG / SHORT отдельно от Buy / Sell | One-Way Sell сокращает Long либо увеличивает Short по текущему состоянию; Hedge требует точный position_slot |
| **PnL/расход** | знак: прибыль **плюс**, убыток/затрата **минус**; раздельные компоненты | Известная комиссия отрицательна в чистом результате, funding **может** быть доходом; не складывать агрегат с его составляющими |
| **Неизвестное значение** | UNKNOWN / MISSING / UNVERIFIED + причина, **не** 0 | 0 подтверждать источником, пустую строку/None/отсутствующую секцию трактовать по схеме и контексту |

Использовать точные десятичные записи при нормализации, не округлять до проверки **tick_size / qty_step / min_qty**; неверная точность может сделать цену/объём неисполнимыми. При нескольких валютах каждая конверсия — **отдельная запись**: amount, from_ccy, to_ccy, verified_rate, rate_source, rate_time, haircut/fee если применимы, output_amount. **Нельзя** превращать USD в USDT по предположению 1:1 и затем считать лимит 30% соблюдённым.

### 2.3. Временные признаки статусов позиций, ордеров и ботов

**Позиция:** NONE/FLAT (**подтверждённый** qty=0), OPEN, CLOSING (только если подтверждены связанные действия) либо UNKNOWN. LONG/SHORT — независимая направленность открытой позиции. Hedge Mode допускает две стороны одного символа в отдельных слотах; One-Way не превращает Buy/Sell в отдельные позиции.

**Биржевой ордер:** PREPARED/PLANNED (*не биржевой*), NEW/ACTIVE, PARTIALLY_FILLED, CONDITIONAL_PENDING, FILLED, CANCELLED, REJECTED, EXPIRED либо UNKNOWN. **Нормализованные состояния** не равны точным enum Bybit; сохранить original_status и mapping_source. Считаются потенциально открывающими **оставшиеся** количества активных/частичных/условных ордеров, а не полностью исполненные qty_total. Терминальное состояние подтверждается по согласованному снимку/истории, а не предполагается по исчезновению из одного ответа. Проверить пагинацию и фильтры активных/условных заявок.

**Бот/сетка:** виртуальный план может находиться в состояниях NOT_SUBMITTED, ACTIVE_WITH_EXCHANGE_ORDER, TRIGGER_WAITING, FILLED_LEVEL, CANCELLED_LEVEL или UNKNOWN. Наличие настройки IN в боте не доказывает, что одноимённый ордер уже существует на бирже, **и наоборот**. Одно звено сетки может быть частично исполнено и частично ожидать; будущие обязательства и уже сформированная позиция не являются одной величиной.

Если статус, объём оставшейся части, режим позиции или связь с биржей неизвестны, отмечать **UNKNOWN** и переходить к ограниченной/консервативной сценарной ветви. **Консервативное включение неопределённой нагрузки в стресс** не доказывает готовность к торговле.

## 3. Состояния расчёта, инварианты и стартовые синтетические проверки 05.1

### 3.1. Логическая модель переходов

| Состояние расчёта | Что в него включать | Следующий переход |
|---|---|---|
| **S0 — CURRENT_PORTFOLIO** | Подтверждённые фактические позиции, текущая Equity/IM/MM и фактически зарезервированные биржей обязательства, действующие ордера и боты **связаны по идентификаторам** | Наложить ещё не исполненные обязательства, **не добавить заново уже учтённую маржу/исполнения** |
| **S1 — PENDING_ORDERS** | Все активные, частично исполненные и условные заявки; сопоставленные/не сопоставленные с ботами будущие уровни | Смоделировать допустимые последовательности исполнения, не считать условную заявку уже исполненной |
| **S2 — FILLED_LEVELS** | После каждого условного исполнения изменить позиционный размер/сторону, баланс и потребность в марже, расходы и ещё не исполненные остатки | Повторить для следующего уровня или сценария; статус и актуальность источников в модели не улучшаются автоматически |
| **S3 — STRESSED_PORTFOLIO** | Ценовые/корреляционные шоки для **всех** позиций и оставшихся ордеров, меняющиеся Equity, IM/MM, funding, исполнение/проскальзывание | Сравнить с FR; если нет проверенной модели/входов, вернуть неопределённость, не READY |

Это **не алгоритм расчёта маржи/ликвидации**: формулы и правила допуска для S1–S3 разрабатываются в 05.2–05.6. Формальная ветвь состояния не означает, что ордер обязательно исполнится, а стоп гарантирует выход.

### 3.2. Предотвращение двойного счёта

1. **Единственная идентичность заявки:** ключ (account_scope, symbol, orderId или достоверно сопоставленный orderLinkId, position_slot) и версия обновления. Один и тот же orderId из T02, T04 и скриншота бота — **одна** биржевая заявка. При невозможности достоверно установить соответствие хранить две записи в группе **POSSIBLE_DUPLICATE**, не делать неподтверждённый точный итог.
2. **Уже исполненная часть:** qty_filled отражается в позиции/исполнениях S0, **не резервируется вторично** как будущий IN. Для заявки проверять qty_total = qty_filled + qty_leaves **лишь когда единицы и смысл полей совпадают**. При несогласованных полях — CONFLICT.
3. **План ≠ ордер:** уровень бота без подтверждённого биржевого orderId — отдельное будущeе сценарное обязательство; связь с биржевой заявкой устанавливать только по доказуемому bot_level_ref ↔ order_ref. Не удалять «дубли» лишь по равным ценам и размерам — два разных ордера могут совпасть.
4. **Маржа сейчас ≠ маржа будущих IN:** если биржевой totalInitialMargin уже включает некоторую маржу **активных ордеров**, нельзя заново прибавить ту же маржу к текущему IM. Прогноз строить как **новое состояние после изменения/исполнения** и/или явную добавочную маржу. Без разбивки значения и способа учёта — NOT_VERIFIED.
5. **PnL и расходы:** агрегатный Equity может уже учитывать unrealized PnL; не прибавлять его второй раз. Сумма позиций и ботов с одним underlying исполнением не удваивает realized PnL/fee/funding. Не складывать гривны/доллары/USDT без конверсии.
6. **Состав портфеля:** объединять позиции по доказанной биржевой идентичности. Отдельные стороны Hedge Mode нельзя взаимно «обнулить» для FR-033, если обе являются открытыми позициями.
7. **Сценарное ветвление:** если все уровни IN не могут исполниться одновременно (OCO, reduce-only, взаимное исключение), учитывать это **только при подтверждённых условиях платформы/биржи**. При неизвестных условиях не обещать заведомо невозможную либо гарантированно безопасную траекторию.

### 3.3. Обязательные инварианты нормализации

| Код | Инвариант | Ошибка/следствие |
|---|---|---|
| I01 | Для каждого входа заданы instrument_id, **рынок** и точная валюта | Spot/Perp или USD/USDT смешаны → CONFLICT / NEEDS_DATA |
| I02 | Каждая величина имеет тип (price/qty/notional/Equity/IM/MM/rate) и единицу | qty в USDT «как монеты» → недопустим расчёт |
| I03 | Стоимость и обеспечение объединяются только после подтверждённого перевода валют и типа счета | USD totalEquity + USDT IN без FX → UNVERIFIED |
| I04 | Время поля относится к наблюдению или явному proxy, не к пересылке | Датировка по retrieved_at при неизвестном наблюдении → TIME_UNVERIFIED |
| I05 | Снимок R3 охватывает **всё** и не инвалидирован событием | Пропуск условных заявок либо изменение после T02 → NEEDS_DATA |
| I06 | Характеристики Cross/Isolated/One-Way/Hedge согласованы с аккаунтом/позицией | Нельзя по одному значению вычислить Cross ликвидацию |
| I07 | Позиционные qty неотрицательны, direction и slot заданы отдельно | Sell ≠ автоматически SHORT; обратная сторона не создаётся предположением |
| I08 | Для каждого ордера известны статус, оставшееся количество, действие и режим (или UNKNOWN) | Нельзя считать qty_total будущим риском при частичном исполнении |
| I09 | Соответствие уровня бота и ордера установлено идентичностью, не совпадением цены | Не удалять разные заявки и не дублировать одну заявку |
| I10 | В отчёте Equity/IM/MM/available funds не объявляются взаимозаменяемыми | Формальная «занятая маржа = Equity − available» без подтверждения запрещена |
| I11 | Процентные ставки хранятся с типом fraction/percent и периодом | 0.0001 fraction = 0.01%; иначе метод/расход ошибочен |

| I13 | Рассчитанные, наблюдаемые и гипотетические значения явно различены | Нельзя повысить доверие предположения до официального факта |
| I14 | При отсутствии проверенной маржинальной или убытковой модели финальное READY не выдается | Нормализованный вход ≠ доказательство FR-030/032/038/040 |

Инварианты задают **условия допустимости будущего вычисления**, не числовые результаты FR-027–FR-040. Приоритет **известного нарушения REJECTED** над недостатком данных сохраняется.

### 4.1. Проверяемые требования и паспорт состояния

Объект шага — **FR-029: ≤30% текущего Equity** для максимальной совокупной планируемой Initial Margin; **FR-031: рекомендованное плечо ≤5×**; **FR-033: не более трёх одновременно открытых позиций** с учётом достижимых исполнений и отдельных Hedge-сторон; **FR-034: 100% финансирования всех будущих IN + буферы**.

**Для проверки нужны:** T02 (весь фьючерсный счёт, полный охват, UTA/account mode и обеспечительные контуры, текущие позиции, активные и условные ордера, боты), соответствующие T03/T04 с целой сеткой, подтверждённое текущее Equity, валюта оценки и время, доступные средства, **фактическая** учтённая начальная маржа позиций/заявок либо верифицированная модель получения её из исходных полей. Для каждой позиции и заявки необходимы symbol, category=linear, settleCoin=USDT, размер в правильной единице, позиционный слот/направление, статус, leavesQty, reduceOnly/closeOnTrigger, связь бота с биржевым orderId, цена и условия исполнения. Для прогноза — актуальные ограничения инструмента, ступень риска, расходы и явно проверенная валютная конверсия, если есть USD и USDT.

**Контроль полноты:** закрыть пагинацию всех релевантных категорий, фильтров и субсчетов; отсутствие страницы не означает пустоту. Снимок T02 ≤5 минут для R3, но при любом новом ордере/исполнении/изменении позиции после T02 он немедленно инвалидируется. Mark для риск-оценок ≤2 минут (или строже при условиях рынка) с происхождением и правильным типом цены. Раздельные обеспечительные контуры нельзя складывать в один Cross без доказанной биржевой модели.

[Wallet Balance V5](https://bybit-exchange.github.io/docs/v5/account/wallet-balance) указывает `totalEquity`, `totalInitialMargin`, `totalMaintenanceMargin`, `totalAvailableBalance` в **USD** для применимых account-wide агрегатов Unified Account, а `coin.totalOrderIM`/`coin.totalPositionIM` — в валюте актива; account-wide агрегаты не применимы одинаково к Isolated и Portfolio Margin. Валюта счета **не становится USDT** из-за USDT Perpetual. Пустое поле не является нулём. При отсутствии проверенной конверсии/применимой модели — `UNVERIFIED`; `notional/leverage` не заменяет подтверждённую биржевую IM.

### 4.2. Экспозиция и исполнение будущих заявок

Для подтверждённого прямого linear-контракта с qty в базовом активе и контрактным множителем 1:
- `notional_quote(q,p)=|q_base| × p_quote/base`, единицы `base × quote/base = quote`; в иных спецификациях требуется верифицированный множитель.
- `gross_notional(s)=Σ |q_position(s)| × price_basis(s)` по всем позиционным слотам **одной валюты**, после устранения задвоений и со ссылкой на источник цен; `net_delta` и `gross` не взаимозаменяемы.
- Будущее увеличение экспозиции моделируется по **остатку** `leavesQty` каждой допустимой заявки, не по `qty_total` и не повторно по уже исполненной `cumExecQty`. Реальные цены рыночного/условного исполнения могут отличаться от Mark, Last и trigger.
- В One-Way `q_signed>0` Long, `q_signed<0` Short, Buy добавляет `+qty`, Sell `−qty`: `q_after=q_before+signed_fill`. Встречный ордер сначала может уменьшать, затем развернуть позицию, если поддерживается. Reduce-only **не должен** открывать противоположную позицию; не предполагать, что он обязательно исполнен.
- В Hedge Mode (`positionIdx=1` Long, `positionIdx=2` Short) рассматривать две стороны отдельно; side Buy/Sell не определяет действие без слота, режима и текущей позиции.
- Действующая биржевая заявка, отражённая также в T04 как IN-уровень, — **одно обязательство**, если связь доказана по устойчивому идентификатору; совпадение цены само по себе не подтверждает дублирование. Подтверждённо разные orderId учитываются отдельно.
- Открытые, частично исполненные, условные и виртуальные IN участвуют в дереве **достижимых** сценариев. Условная заявка без занятой IM **сейчас** не означает нулевую будущую нагрузку. Стоп/OUT/TP не освобождает маржу в прогнозе до подтверждённого исполнения; подтверждённое взаимное исключение/Reduce-only учитывается.

**FR-033:** `positions_count(s)=число уникальных (account_scope,symbol,position_slot) с ненулевым фактическим размером`. Проверка `max_s positions_count(s) ≤ 3` по текущему состоянию и всем существенным *достижимым* сценариям после планируемых ордеров. Два IN одной позиции не создают две позиции; две противоположные Hedge-стороны — **две**. Выявленная достижимая четвёртая позиция при увеличении риска → `REJECTED`. Если слот не подтверждён, точное число недоказано.

### 4.3. Маржа: считать новые состояния, а не сумму скриншотов

Обозначения (только для одной верифицированной валюты `C` и одного обеспечительного scope):
- `E0[C]>0` — **текущий** Equity на согласованном T02.
- `IM0[C]` — действительная **совокупная** Initial Margin по подтверждённому применимому аккаунту; если она **включает order IM**, то её нельзя снова прибавить.
- `IM_s[C]` — начальная маржа **полного состояния s** после конкретной последовательности исполнений, рассчитанная по **проверенной биржевой модели и действующим риск-ступеням**, либо по исходной сумме плюс обоснованным **чистым дельтам**.
- `E_s[C]` — сценарная Equity после исполнения/PnL/затрат, **отдельна** от нормативной текущей `E0`.

`ratio_current = IM0/E0 ×100%`. `ratio_planned = max_{s∈reachable} IM_s/E0 ×100%` — сравнить с **30% текущего Equity**; указать worst-case state и подтверждённую модель. При изменении фактического Equity или T02 до принятия решения получить новый `E0`. Для стрессов отдельно показывать `IM_s/E_s`, **не подменяя** этим установленную базу FR-029.

**Не считать `IM_s=IM0+Σ(orderIM уже забронированных)+Σ(positionIM после fill)`.** Когда действующий ордер исполнен, часть `orderIM` переходит в `positionIM`: в *упрощённой проверенной учётной модели* `IM_next=IM_prev − released_orderIM + increased_positionIM + other_verified_deltas`. Это **учётное преобразование**, не универсальная биржевая формула. При смене risk tier, account mode, funding, исполнении других позиций или неизвестной семантике IM **не обещать точное число**.

`notional/leverage` — возможная объяснительная аппроксимация для прямого linear при *явно зафиксированных* параметрах, но не доказанная IM для Cross, Portfolio или конкретной ступени Bybit. Risk Limit V5 ([официальная схема](https://bybit-exchange.github.io/docs/v5/market/risk-limit)) содержит `riskLimitValue`, `maintenanceMargin`, `initialMargin` и `maxLeverage`; числовые процентные поля интерпретировать **по подтверждённой документации метода**, а не угадать по строке `"1"`. Верхняя оценка IM разрешена для доказательства лимита только если **доказано, что она действительно верхняя во всех существенных ветвях**.

**FR-031:** рекомендованное плечо новых/изменяемых позиций ≤5×, с проверкой в каждой ветви. Cross + Hedge имеет связанную настройку buy/sell leverage, а Isolated Hedge может иметь разные значения ([Bybit V5 Set Leverage](https://bybit-exchange.github.io/docs/v5/position/leverage)). Portfolio Margin может не иметь применимого поля leverage: не интерпретировать пустое значение как 0× или выполнение ограничения.

**Правило принятия локального результата:** если подтверждённая существенная ветвь имеет `IM_s >0.30 E0`, нарушает ≤5× либо число позиций >3 — `REJECTED` для нового увеличения риска. При недостатке обязательных входов — `NEEDS_DATA`, при неподтверждённой модели/FX/конфликте — `UNVERIFIED`. Равенство 30% проходит **только эту проверку**. Сведения `PASSED_FOR_SUBSET` и `FAILED` — технические метки, не пятый статус торговой готовности.

### 4.4. Вымышленные контрольные примеры

**SYN-05-02-A — полная IM после последовательных IN.** Все значения синтетические и в **USD**, без смены риска и Equity: `E0=1000`, `IM0=250`, **40 уже включены в 250** как order IM. Исполнение этого ордера освобождает 40 order IM и потребляет 42 position IM: `IM_A=250−40+42=252`. Следующий **ещё не учтённый** IN увеличивает IM на 38: `IM_B=252+38=290`. Нормативные отношения: `250/1000=25%` и `290/1000=29%`. Ошибочные `250+40+42` и `250+40+42+38` дважды учитывают ордер. **29% проходит только иллюстративный FR-029**, не доказывает реальную Bybit IM и не даёт `READY`.

**SYN-05-02-B — полный бюджет будущих IN.** `R_available=80 USD` уже **после** ранее учтённых блокировок; новое требование IM будущих уровней `40 USD`, синтетически ограниченные в модели fees `8`, slippage `12`, funding `6`: `R_required=40+8+12+6=66 USD`, условный остаток `14 USD`. Это **только одна вымышленная ветвь**; при отсутствии доказанного верхнего предела комиссии/funding/slippage полный резерв `UNVERIFIED`, при Cross другие убытки конкурируют за те же 80 USD.

**SYN-05-02-C — число позиций.** BTC LONG + ETH SHORT = 2 слота, новый SOL LONG = 3, потенциальный ADA SHORT одновременно = 4 → подтверждённое превышение FR-033 → `REJECTED` для расширения. Два разных IN той же SOL LONG остаются одним слотом. Hedge BTC LONG и Hedge BTC SHORT — два слота, не ноль.

**SYN-05-02-D — One-Way разворот.** `q_start=−2` SOL, Buy qty=3 при подтверждённом разрешённом развороте: после Buy1 → −1 Short, Buy2 → 0 FLAT, Buy3 → +1 Long. Ни на одном этапе только этой ветви не возникают две одновременные One-Way позиции.

**SYN-05-02-E — стресс отличается от текущего Equity.** Для `IM_s=290 USD`, `E_s=700 USD`: `stress_margin_ratio=290/700≈41.43%`, но нормативное сравнение по текущей базе `E0=1000 USD` остаётся 29% **до нового фактического снимка**. Эта отдельная стресс-величина не утверждает соблюдение остальных лимитов.

## 5. Полное покрытие будущих усреднений и буферы (шаг 05.2)

### 5.1. Метод FR-034

В одном реестре объединить по **достоверным ссылкам** существующие активные/условные биржевые ордера, планируемые уровни IN каждого бота, частично исполненные остатки, а также обеспечение и другие обязательства всех связанных контуров. У одного физического orderId может быть несколько упоминаний из T02/T04, но физически он учитывается **один раз**. Разные реальные ID с одинаковой ценой — разные заявки.

Для каждого существенного достижимого сценария полного исполнения оставшихся IN определить:
1. `new_collateral_s` — **чистую** дополнительную потребность в обеспечении после уже забронированной IM; не вычитать один и тот же резерв два раза.
2. `fees_s` — комиссии **входа и возможного закрытия**, документировать ставку, способ расчёта и границы.
3. `slippage_s` — денежную стоимость неблагоприятного исполнения при **доказанной сценарием границе**; не называть неограниченную неопределённость нулём.
4. `funding_s` — потенциальный расход за подтверждённые интервалы и по сценарным ставкам/знакам; не считать всегда расходом и не засчитывать доход без доказательства.
5. `other_needs_s` — прочие **не входящие ранее** денежные обязательства и потери, конкурирующие за обеспечение.

`R_required = max_s (new_collateral_s + fees_s + slippage_s + funding_cost_s + other_non_overlapping_needs_s)` по **всем полным допустимым последовательностям будущих IN**. Если часть расходов/маржи **не ограничена проверенной моделью**, нельзя утверждать существование окончательного числового `R_required`; можно показать условную сумму с допущениями.

`R_available` берётся из подтверждённых **реально доступных** средств того же обеспечительного scope/валюты **после** известных занятых биржей ресурсов и конкурирующих обязательств; буфер, названный пользователем «резерв», **не изолирован физически при Cross**. Нельзя повторно добавлять фактически заблокированную order IM к доступной сумме, и нельзя выводить `available = equity − IM` без проверенной семантики UTA/режима.

**Проверка:** `R_available ≥ R_required` и достаточность **в каждой существенной ветви**, плюс отдельно FR-029/031/033. Даже положительный условный запас не гарантирует исполнение при резком изменении Cross Equity или биржевых правил — нужна риск-модель 05.4–05.6. Не подменять 100% **будущей маржи + буферов** резервированием 100% денежного номинала, если биржа этого не требует.

### 5.2. Алгоритм для агента

1. Проверить корректность рынка, счёта, timestamp/валют и полноту снимка T02, всех позиций, *условных* заявок, ботов и T04; при новом событии обновить T02.
2. Сопоставить по устойчивому orderId заявки T02 и уровни T04, отделить исполненный `cumExecQty` от будущего `leavesQty`; неизвестную связь оставить как `POSSIBLE_DUPLICATE/UNVERIFIED`, не выбирать лучший результат.
3. Построить достижимые ветви с частичными исполнениями, режимами One-Way/Hedge, разными ботами, изменениями Equity, риск-ступеней, активными и ещё не активированными условными заявками; исключить только *доказанно* взаимоисключающие ветви.
4. По подтверждённой биржевой методике/полному набору согласованных агрегатов получить `IM_s` и `R_required_s`, вывести максимумы и сценарии. Если нет метода — оставить `UNVERIFIED`, а не подставлять `notional/leverage` как факт биржи.
5. **Отдельно** проверить FR-029 ≤30% E0, FR-031 ≤5×, FR-033 ≤3 слота, FR-034 100% полного покрытия; показать разбивку на текущую занятую IM, дельту IM и независимые буферы.
6. Не учитывать будущее исполнение стопа/OUT как **гарантированное** снижение риска; при доказанном превышении → `REJECTED`, иначе конкретно указать недостающие источники/модель.
7. Явно сообщить, что шаг **05.2 не проверяет liquidation price, предельный убыток Short или стресс FR-038** и не может сам дать `READY`.

### 5.5. Граница результата 05.2

Прохождение **только** FR-029/031/033/034 означает `PASSED_FOR_SUBSET`, а не `READY`; нарушение — локальное `FAILED` с указанием действительного торгового статуса `REJECTED` при доказанном жёстком превышении. ## 6. Ликвидация Isolated Margin: Long и Short (05.3)

> **Статус: 05.3 `COMPLETED / APPROVED`, 15.10.2026** ([приёмка](risk-05-03-validation.md#5-формальная-приёмка-шага-053--15102026)). Правила ниже применяются к **подтверждённому UTA Isolated, Bybit USDT Perpetual (linear)**; они не подменяют реальную проверку позиции пользователя. **В рамках этого раздела Cross/Portfolio Margin не моделируются**; Cross рассматривается отдельно в §8–§9 шага 05.4, max loss Short (05.5) и четыре стресс-теста (05.6) не выполнены. Настоящий `READY` этим разделом не разрешён.

### 6.1. Официальная применимая формула — не старая формула 2024 года

[Bybit: UTA Trading Rules — Liquidation Process](https://www.bybit.com/en/help-center/article/UTA-Trading-Rules-Liquidation-Process), обновлено **07.08.2026**, даёт формулы для USDT Isolated и фиксирует **Mark Price** как триггер ликвидации. [Bybit: The New Margin Calculation](https://www.bybit.com/en/help-center/article/Understanding-the-Adjustment-and-Impact-of-the-New-Margin-Calculation), обновлено **18.06.2026**, документирует изменение алгоритма с **02.09.2025**: в Isolated базовая IM в формуле остаётся связанной с Entry, **MM учитывает Mark**, а риск-ступени могут изменяться при движении Mark и суммарной нагрузке позиций/ордеров. Старую формулу вида `Entry ± (IM−MM)/Qty` с Entry-based MM нельзя объявлять актуальной без проверки версии.

**Область:** UTA Isolated, USDT perpetual, позиция с действительными side/positionIdx и прямой величиной qty в базовом активе; применимые параметры настоящей ступени, договора, комиссии и выделенной маржи. **Не переносить** в Cross, Portfolio Margin, BTCUSD Inverse или BTCUSDC с сессионными особенностями.

Для R3 срок T02 не более 5 минут при **отсутствии событий**, Mark — не более 2 минут или строже при волатильности. Нельзя объявлять актуальность только на основании TTL.

**AMR:** если autoAddMargin включён, дополнительный перевод средств зависит от доступного баланса и биржевых триггеров, не гарантирован заранее. Проверить переключатель, уже осуществлённые пополнения, funding и ручные добавления; при изменении — пересчитать состояние. **Не подставлять `A=0`, если A неизвестна**.

### 6.3. Формулы Bybit USDT Isolated и ограничения

Обозначения: `E` — средняя entry USDT/base, `q` — положительное количество base, `L` — плечо, `r` — ставка поддерживающей маржи **fraction** (например, 0.005 = 0.5%), `D` — вычет MM USDT, `A` — дополнительно внесённая Isolated margin USDT, `f` — комиссия taker **fraction**.

**Long:**
\[
P_{\mathrm{liq,L}}=\frac{Eq-Eq/L-A/(1-f)-D}{q(1-r)}
\]

**Short:**
\[
P_{\mathrm{liq,S}}=\frac{Eq+Eq/L+A/(1+f)+D}{q(1+r)}
\]

Размерность обеих формул — **USDT/base**. Допустимость входа: `q>0`, `E>0`, `L>0`, `0≤r<1`, `0≤f<1`, конечные и корректно классифицированные `A,D≥0`; проверенная применимость одной формулы на соответствующем интервале Mark. **Не складывать повторно входящую в модель комиссию с `A` и не принимать всю position IM за `A`**. Не подменять ставку r процентным числом «0.5» вместо fraction «0.005».

**Критическая проверка ступеней:** риск-ступень зависит от стоимости позиции по Mark, а в некоторых режимах от соответствующих ордеров; при достижении рассчитанного корня она может быть иной, чем сегодня. Рассчитать кандидат в каждом подтверждённом диапазоне r/D, проверить, относится ли кандидат к этому диапазону, учесть возможный скачок MMR **до** корня и определить **первую** опасную границу по неблагоприятному пути. Если не доказаны границы ступеней или исходы конкурирующих заявок, выдавать **`UNVERIFIED`**, а не единственную «точную ликвидацию». Не использовать универсальную величину `notional/leverage` как проверенную полную биржевую модель.

**AMR, funding, комиссия, добавление/изъятие маржи и изменение размера** меняют состояние и требуют нового снимка. Округление цены ликвидации по tick только для отображения, расчёт порога — с **неокруглёнными Decimal**. Неправомерно переносить расчёт между аккаунтами, формулами устаревшей версии либо USDT/USDC/Inverse.

### 6.4. FR-032: направленное расстояние **от Mark**

Для каждой текущей позиции и каждой существенной ветви будущей сетки, при доказанно применимой цене ликвидации:

- **Long:** `d_L = (Mark − P_liq,L) / Mark × 100%`.
- **Short:** `d_S = (P_liq,S − Mark) / Mark × 100%`.
- Требование **`d≥15%`**. Ровно 15% допускается только для FR-032; 14.999% недопустимо, даже если в интерфейсе округлено до 15.00%.
- При `Long P_liq ≥ Mark` либо `Short P_liq ≤ Mark` направленный запас ноль/отрицателен; **`abs(liq−Mark)` и деление на entry запрещены**.
- Если **подтверждённая** оценка `d<15%` → `REJECTED` для новой/увеличенной нагрузки. Если модель/источник ликвидации недостоверны → `UNVERIFIED`; обязательный отсутствующий факт → `NEEDS_DATA`. Известный жёсткий провал имеет приоритет.
- Текущий снимок Mark **не равен будущей Mark при исполнении IN**: нельзя при пересчёте после Short-IN на 120 использовать старую Mark=100 как доказательство запаса. Требуется сопоставимый свежий Mark для каждого подтверждаемого состояния.

Проверка 15% **не** подтверждает FR-030 (предельный убыток), FR-029/034 (портфель/резерв), FR-038 (стрессы) либо действительность формы P02. Стоп, выставленный по Last, может не предотвратить ликвидацию по Mark.

### 6.5. Пересчёт после IN и Hedge

1. Для **реально исполненного увеличения той же стороны** при подтверждённом методе учёта усреднённого входа: `q_new=q_old+q_fill` и `E_new=(q_old E_old+q_fill P_fill)/(q_old+q_fill)`; не переносить это равенство на разворот One-Way через ноль.
2. Затем пересчитать **фактическую** isolated IM, внесённую дополнительную маржу A, изменившиеся fee/funding, risk-tier/MMDeduction и обе применимые стороны. `A` не равняется `q_new×E_new/L`.
3. Для IN, ещё не исполненного, строить **условную ветвь** со своей гипотетической Mark, а не обновлять реальное состояние S0. Полные сетки и другие боты не игнорировать.
4. В Hedge Long/Short на одном символе — отдельные `positionIdx`, позиции, маржа и ликвидационные пороги; неттинг запрещён. Если One-Way полностью закрыл Short и открыл Long, это новая сторона с отдельно вычисленными входами.
5. Если ступень/AMR/заявка/маржа сменилась после T02, нужна новая целостная версия T02/T03/T04 даже внутри TTL.

### 6.6. Порядок ответа агента и границы применения

Проверить (а) рынок/режим/источники; (б) фактические q/entry/leverage/extra margin/risk tier/rate/deduction/fee; (в) Mark и событийную свежесть; (г) путь изменения риск-ступени и все IN; (д) формулу кандидатов, корректность их диапазонов и ближайшую ликвидационную опасность; (е) сопоставление с биржевой `liqPrice` и её временем/непустотой (не назначать произвольный допуск совпадения); (ж) отдельный порог FR-032 в текущей и прогнозируемых ветвях.

В отчёте представить **источники, версию, валюты, формулу, числа и неокруглённый результат, risk-tier путь, оценочную liqPrice, d и локальный статус**, а также отсутствующие поля и требуемый следующий ввод. Не публиковать приватные UID/API-ключи в GitHub. Биржевая `liqPrice=""` может означать значение вне допустимых ценовых границ; это **не** обещание «ликвидации нет». Cross отдельно остаётся RV-02/05.4.

### 8.1. Нормативный принцип Bybit после изменения 02.09.2025

В [официальном описании корректировки маржи](https://www.bybit.com/en/help-center/article/Understanding-the-Adjustment-and-Impact-of-the-New-Margin-Calculation) указано: **с 2 сентября 2025 г. для UTA Cross IM и MM рассчитываются от Mark Price, а не Entry Price**, Risk Limit Tier зависит от Mark и совокупного объёма позиций **и ордеров**. Это касается расчётных условий режима, а не означает, что модель может пренебречь торговыми комиссиями, funding, заемными активами, haircut и режимом Hedge.

[Trading Rules: Liquidation Process — вкладка Cross](https://www.bybit.com/en/help-center/article/UTA-Trading-Rules-Liquidation-Process?tabIndex=2) (обновлено 07.08.2026):
- Главная величина — **Account Maintenance Margin Rate (MMR)**. При **MMR ≥100%** запускаются защитные действия/ликвидационная процедура; **при MMR ≥160%** описан механизм полного принятия позиций движком (с оговорёнными исключениями). **100% — запуск процедуры, а не обещание немедленной полной ликвидации каждого инструмента**.
- До ликвидации возможны отмена увеличивающих ордеров, погашение заимствований, отмена остальных ордеров, закрытие полностью хеджированных позиций и снижение открытой позиции/риск-ступени. Эти операции **изменяют маржу и Equity** — путь необходимо пересчитывать.
- Цена ликвидации одной Cross-позиции, отображаемая в интерфейсе, **динамическая и справочная**, зависит от Equity, UPL, других позиций, MM и доступного обеспечения. Она **не является независимой фиксированной гарантией**.
- **IMR ≥100%** ограничивает размещение новых увеличивающих риск деривативных ордеров, но не равен событию ликвидации. Правила ограничений на займ/заказы не переносить на все аккаунты без проверки.

**Отдельно:** Portfolio Margin — **другой режим**, основанный на стресс-оценке risk units; формулу UTA Cross к нему не применять. Legacy/другие account modes, несколько субсчетов и не подтверждённый тип UTA — `UNVERIFIED` до отдельной спецификации. Вся область ограничена заявленной первой биржей Bybit, USDT Perpetual как торговыми инструментами, но **учитывает иные продукты/долги/обеспечение UTA, если они фактически находятся в общем Cross scope**.

### 8.2. База Account MMR и IMR: корректные знаменатели

В [Bybit: Trading Terms and Formulas in UTA](https://www.bybit.com/en/help-center/article/Glossary-Unified-Trading-Account) (актуальные значения и применимость сверять с аккаунтом) для Cross заданы:

\[
Account\ MMR(s)=\frac{TotalMaintenanceMargin(s)}{MarginBalance(s)-HaircutLoss(s)+OrderLoss(s)}
\]

\[
Account\ IMR(s)=\frac{TotalInitialMargin(s)}{MarginBalance(s)-HaircutLoss(s)+OrderLoss(s)}
\]

Здесь все суммы относятся **к одному UTA Cross-account и общему измерению USD**, а `OrderLoss` в этой формуле — **подписанная величина неположительного значения** при неблагоприятных ордерах. **Не менять плюс на минус второй раз.** Базовое поле `totalMarginBalance` в V5 и рассчитанный *с учётом* haircut/order-loss знаменатель — **разные величины**. По [V5 Wallet Balance](https://bybit-exchange.github.io/docs/v5/account/wallet-balance) применимы account-wide `totalInitialMargin`, `totalMaintenanceMargin`, `accountIMRate`, `accountMMRate`, `totalMarginBalance`, `totalEquity`, `totalAvailableBalance`, а активы могут иметь `spotBorrow` и свои collateral values.

**Двойной счёт запрещён:** если используем прямо **наблюдаемый `accountMMRate` Bybit**, не вычислять второй раз его знаменатель с неизвестными haircut/order-loss и не объявлять два результата независимыми измерениями. Если считаем свой знаменатель, установить, от каких исходных полей он получен, включают ли агрегаты долги/spot margin и учётные потери, каким способом проведена конверсия каждой монеты в USD. `totalAvailableBalance` **не** тождественен `MarginBalance−MM`, и не должен становиться знаменателем MMR.

**MM/IM полных состояний:** `TotalMaintenanceMargin(s)` и `TotalInitialMargin(s)` должны включать относящиеся к общему обеспечению позиции, соответствующие активные/условные обязательства в момент их исполнения, стоимость заимствований, fees, MM deduction, динамические Mark-based tier и особенности связанного Hedge. **Точную функцию MM_bybit(s) нельзя объявить доказанной только по записи “MMR=…” и формуле выше.** Позиционная MM и требования для Hedge отличаются от суммы абсолютных «лонгов и шортов» (одинаковые Hedge стороны **не** всегда допустимо неттировать). Биржевая исходная сводка — наблюдение *текущего* MMR, а не доказательство будущего `MM_s`.

**Допустимая математика:** `D(s)=MB(s)−HL(s)+OL(s)` с единицей USD. При подтверждённом `D>0` и `MM≥0`, `MMR=MM/D×100%`. Если `D≤0` при положительной MM, **запас обеспечения исчерпан / критическое состояние**; **не** считать отрицательное MMR отрицательным риском и не вычислять фиктивный «безопасный» процент. Если доказано, что состояние с `D≤0` достижимо, оно нарушает допуск новой нагрузки и должно быть явно отмечено как критическое. При `MM=0` и `D≤0` численное соотношение неоднозначно; запросить фактическую биржевую логику, не присваивать 0%.

### 8.3. Набор входов для моделирования Cross

Подтвердить **в один момент T02** все требования ``1–5: account_type=UNIFIED, выбранный UTA Cross, действующий collateral scope и collateral eligible assets, полную wallet/position/order информацию, все дополнительные категории внутри UTA и все боты/будущие уровни. Сохранять символ, qty/позиционный слот, side, entry, Mark, среднюю стоимость после fill, PnL, IM/MM, risk tier, комиссии, funding, FX, haircuts, Spot/borrow liabilities, действительные ограничения инструментов, cost/order-loss.

Для модельного перехода `S0→S1→S2→S3` обязательны:
1. **Согласованное S0:** фактические `MB0, MM0, IM0, HL0, OL0` *или* прямое `accountMMRate0/IMRate0` с отдельной отметкой, что это только текущее наблюдение. Сверить рассчитанную MMR с возвращённой биржей в **той же версии/времени**; при конфликте — `UNVERIFIED`.
2. **Изменение Mark по каждому инструменту:** не переписывать `Entry` ценой Mark. По каждой позиции заданного линейного контракта с проверенной спецификацией `UPL_i(s)=signed_qty_i×(Mark_i(s)−Entry_i)` в quote, с отдельным преобразованием в USD, зафиксированными fee/funding/rollover и курсом. `MB_s` получать из неизменных начальных **кошельковых и заемных компонент** плюс пересчитанный UPL и другие подтверждённые изменения — **не добавлять новый UPL поверх MB0, если он уже включён**. Для дельты проще: `MB_s=MB0+Σ[UPL_i(s)−UPL_i(0)]−verified_cost_delta+verified_collateral_delta+other_ledger_delta`. Суммы разной валюты не складывать без верифицированных FX/haircut. Положительный UPL и возможность использовать его как доступную маржу могут зависеть от правил платформы; брать актуальную биржевую трактовку.
3. **Новые заявки и боты:** полные активные/условные IN, Hedge/One-Way, частичные исполнения и потенциальная отмена/срабатывание. Один действующий orderId между T02 и T04 не добавлять два раза. Учесть влияние реальных order-loss, order IM, fees и будущих уровней. Взаимоисключение допустимо только по подтверждённым биржевым свойствам.
4. **MM_s, IM_s:** актуальные **Mark-based** tier для *объединённой* стоимости позиций и ордеров, tier deductions, leverage/hedge/spot borrow. При отсутствии полной биржевой функции — `UNVERIFIED`, **не** заменять ее фиктивной суммой `Σ|qty×Mark|/leverage`.
5. **Account state:** `MB_s, HL_s, OL_s, MM_s, IM_s, account MMR_s, IMR_s`, курс и provenance, статус доступности; на каждом событийном изменении новая версия снимка. Ставки/буферы и риски всех позиций нужны **одновременно**.

### 8.4. Условия ликвидации, траектория и FR-032

**Определение событийного риска:** на заданном **векторном** неблагоприятном пути `γ(t)={Mark_BTC(t),Mark_ETH(t),…,orders(t),FX(t),collateral(t),fees(t)}`, где `t∈[0,1]`, вычислить все `S(t)`, `D(t)` и MMR. **Первое** достижение `MMR≥100%` или подтверждённого более раннего риска (неположительный знаменатель, принудительное действие, неучтённый trigger) — начало *процедуры управления риском*, **не цена гарантированной полной ликвидации конкретной позиции**. Наличие `MMR0<100%` ничего не доказывает о максимальном безопасном движении.

**FR-032 относится к неблагоприятному расстоянию от текущей Mark:** для Long падение до `0.85×Mark0`, для Short рост до `1.15×Mark0` — **15%-ные рубежи каждой стороны**. Однако Cross может достигнуть 100% MMR **при меньшем изменении целевой позиции** из-за одновременного движения другой монеты, изменения обеспечения/курса, funding или исполнений сетки. Поэтому:
- Построить **однофакторные** пути каждой позиции (прочие Mark и события фиксированы) и **согласованные совместные стресс-пути** и ветви всех ордеров; показать первое критическое событие и неблагоприятное изменение **каждой** позиции на том же пути.
- Если уже существует **доказанный достижимый** существенный сценарий с MMR≥100% **до 15%-ного неблагоприятного движения** позиции, это означает **неподтверждённое требуемое расстояние и выявленный опасный сценарий**. В зависимости от доказанности применимой полной модели — установленное нарушение FR-032 → `REJECTED`; если только условный стресс без подтверждения применимости — `UNVERIFIED` для FR-032, даже если сценарий демонстрирует риск.
- **Нельзя** доказать «≥15% до Cross-ликвидации для всего портфеля» проверкой одной монеты при зафиксированных других, если совмещённые траектории не охвачены. Для подтверждения требуются либо проверенная консервативная **верхняя граница Account MMR ниже 100% на всём согласованном множестве существенных сценариев до 15%-ных рубежей**, либо иной подтверждённый механизм применения FR-032. Невозможно допускать все мыслимые произвольные шоки как гарантированно безопасные.
- **Не выводить настоящую Cross LP** прямой инверсией `MMR=100%` для одной цены, если другие переменные не фиксированы подтверждённо. Динамический справочный `liqPrice` Bybit — отдельное наблюдение с временем/составом аккаунта, не гарантированный неизменный уровень. Нельзя применять к Cross [формулу Isolated 05.3](#63-формулы-bybit-usdt-isolated-и-ограничения).
- При доказанном нарушении жёсткого лимита (в том числе FR-029/031/033/034) → `REJECTED` для увеличения риска; недостающий фактический T02, состав обеспечения, ордера → `NEEDS_DATA`; невалидированная Cross model, динамический tier, противоречивое MMR или недоказанный безопасный диапазон → `UNVERIFIED`. **Статус `READY` по 05.4 сам по себе невозможен**; впереди 05.5–05.8 и P01/P02.

**Запрет ошибочного нулевого риска Hedge:** даже идеально противоположные Long/Short с одинаковым qty могут требовать fee/MM, подвергаться финансированию и биржевым действиям в ликвидационной процедуре; в Cross алгоритм прямо допускает *закрытие полностью хеджированных позиций* для высвобождения маржи. Совпадающие объемы **не** означают нулевую MM или отсутствие любой возможной ликвидации аккаунта.

### 8.5. Как оформлять проверку Cross

| Поле отчёта | Требуемое содержание |
|---|---|
| `scope/inputs` | UTA Cross, дата, market symbols, полная T02/T03/T04, режим One-Way/Hedge, все позиции/ордеры/боты, collateral/borrow/FX |
| `observed_account_risk` | Биржевые accountMMRate/IMRate, totalMM/IM и MarginBalance (USD), время; отдельно вычисленный D, если **полные** HL/OL проверены |
| `model_applicability` | Проверенные функции UPL/fees/borrow/MM-by-tier, источники и версии, допустимые диапазоны и необработанные категории |
| `states/paths` | Начало и последовательность S0–S3, одиночные/совместные шоки, цены Mark всех активов, изменения ордеров и Equity |
| `outputs` | D_s, MM_s, MMR_s, предельные состояния, первая защитная реакция, кратчайшее плохое движение на сценарии, ограничения |
| `limits` | FR-029/030/031/032/033/034/037/038/040 отдельно, какие **НЕ ПРОВЕРЕНЫ**, и конкретный запрос исходных данных |
| `conclusion` | `REJECTED/NEEDS_DATA/UNVERIFIED` с причинами; локальный `PASSED_FOR_SCENARIO` — лишь служебная метка, **не новый trading status** |

**Приоритет:** проверенный жёсткий провал > подтверждённый конфликт/недоказуемая модель > отсутствующий вход. Если не доказана переносимость опубликованной упрощённой иллюстрации Bybit на фактическое UTA, **отказ в заявлении проверенной конкретной LP — правильный результат**, а не незавершённый расчёт, который можно дорисовать.

## 9. Синтетические проверки Cross Margin (05.4)

### 9.1. Контрольные примеры с явно упрощённой моделью

**SYN-CROSS-A — Account MMR (вымышленный USD-account scope):** `MB=900 USD`, `HL=20 USD`, подписанный `OL=−10 USD`, `totalMM=100 USD`, `totalIM=220 USD`. Тогда `D=900−20−10=870 USD`, `MMR=100/870≈11.49425287%`, `IMR=220/870≈25.28735632%`. Это **не** пример liquidation price; показано только верное применение знака Order Loss. Если `accountMMRate` биржи не соответствует 11.49% на **идентичном** снимке при подтверждённой модели, нельзя выбирать удобную версию — `UNVERIFIED`.

**SYN-CROSS-B — общий риск возникает раньше 15% по одному активу:** только искусственная **одновалютная система USDT=USD (задано и доказано как свойство тестовой модели, не предположение для Bybit)**: `MB0=250`, `HL=OL=0`, BTCUSDT LONG `q=5` Entry/Mark100, ETHUSDT SHORT `q=4` Entry/Mark100. Условно фиксируем `MMR_tier=5%` для всех событий, без комиссии и внешних операций (это **только учебная модель**, нельзя так считать реальные fees/tiers). Для совместного пути `BTC(t)=100×(1−0.10t)`, `ETH(t)=100×(1+0.40t)`:
- `MB(t)=250−210t`, `MM(t)=45+5.5t`, `D(t)=MB(t)` (только по условиям данной модели).
- `MMR(0)=45/250=18%`.
- При `t=0.5`: BTC95, ETH120, `MB=145`, `MM=47.75`, `MMR≈32.93103448%`.
- Порог `MMR=100%` достигается при `t*=205/215.5≈0.951276102`, когда BTC≈90.48724 (падение всего **≈9.51276%**), ETH≈138.05104 (рост **≈38.05104%**); `MB=MM≈50.23202`. Следовательно **даже до падения BTC на 15% портфель уже вступил бы в защитную процедуру на этой условной совместной траектории**.
- При `t=1`: BTC90 (−10%), ETH140 (+40%), `MB=40`, `MM=50.5`, `MMR=126.25%` — выше 100%. Пример демонстрирует **нельзя судить о Cross только по LP/Mark BTC**.
- Этот искусственный счёт **не объявлен удовлетворяющим FR-029/034 или полной модели Bybit**. Если для него также были бы **подтверждены** нарушения других лимитов, финальный статус должен быть `REJECTED` по ним независимо от иллюстративности MMR.

**SYN-CROSS-C — ложный «безопасный» знаменатель:** при `MB=40, MM=50.5` значение `MMR=126.25%`, но если MB станет отрицательным, **не** превращать отношение в отрицательный «сверхбезопасный» показатель. Вместо этого критическое отсутствие поддерживающего обеспечения и запрос подтверждённой биржевой процедуры.

**SYN-CROSS-D — бессмысленный фиксированный «BTC LP» при прочих позициях:** в той же *учебной* модели при замороженном ETH=100 из `MB(BTC)=5×BTC−250` и `MM(BTC)=0.25×BTC+20` порог `MMR=100%` получился бы при BTC≈56.84210526; но совместный путь из SYN-CROSS-B приводит к риску уже при BTC≈90.48724. Одна «цена ликвидации BTC» **не обозначает безусловную ликвидационную границу Cross**, поскольку зависит от ETH и других компонентов.

**SYN-CROSS-E — известная фактическая блокировка и недоказанная оценка:** если биржевой accountMMRate с подтверждённого согласованного T02 достиг ≥100%, агент сообщает **наблюдаемый факт о начале/наличии процедуры защиты**, не обещает, что всё уже полностью ликвидировано. Новая увеличивающая риск конфигурация получает `REJECTED` при применимости данного факта. Если есть только экран с текущей LP без актуального account MMR/портфеля, полный вывод `UNVERIFIED/NEEDS_DATA` в зависимости от пробела, не `READY`.

Методика относится к **проверке расчётного максимального убытка одного бота ≤5% текущего Equity** и поведению при невозможности установить верхнюю границу. Область — Bybit USDT Perpetual, весь охват портфеля, Cross/Isolated, все действующие и планируемые IN/OUT, без реальных торговых операций. **RV-03 остаётся OPEN / PARTIAL DOCUMENTARY COVERAGE**: обычный SL и математически удобный сценарий не дают гарантированного предела убытка Short. **05.6 впоследствии принят пользователем**; реальные исторические Mark-тесты и формы P01/P02 не проверены; торговый `READY` недоступен.

### 10.1. Источник правила и разграничение трёх разных величин

[FR-030](requirements.md) требует **расчётный максимальный убыток одного бота ≤5% текущего Equity**, включающий **все усреднения, комиссии, funding и неблагоприятные исполнения**. Не заменять это ни долей начальной маржи, ни суммой номиналов, ни максимальным «минусом на графике» при выбранном стопе.

**Три разных результата**:
1. `L_scenario(ω)` — **убыток по полностью заданной ветви ω** (какие IN исполнились, по каким ценам, сколько удалось закрыть, комиссии, funding, изменение Equity/Mark и защитные действия); корректное число полезно, но **не доказательство максимума**.
2. `L_max(model, Ω) = sup_{ω∈Ω} L_scenario(ω)` — максимум/верхняя граница **по явному множеству допустимых сценариев Ω**. Модель должна обосновать **полноту Ω**, исполнение защитных приказов и границы цен/стоимости/времени, а не просто перечислить несколько удачных примеров.
3. `L_guaranteed_bound` — **проверяемый верхний предел для реально поддерживаемого механизма биржи/аккаунта** при оговорённых внешних условиях. Стоп-маркет с триггером не создаёт такого предела по цене исполнения. Даже оценка `L_max(model, Ω)` не является `L_guaranteed_bound`, когда Ω не доказано охватывает реальные гэпы, ликвидации, изменение обеспечения и непрерывное funding.

**Статус проверки FR-030:** `PROVED_UNDER_SCOPE` — только если есть проверенная консервативная верхняя граница в явно ограниченной и подходящей области; `SCENARIO_ONLY` — расчёт отдельных ветвей; `NOT_PROVABLE/UNVERIFIED` — если нет достаточно строгих границ и биржевой модели; `FAILED` — подтверждённое нарушение жёсткого лимита для применимого предполагаемого решения. Это **служебные статусы** внутри FR, **не** новые торговые `READY/NEEDS_DATA/UNVERIFIED/REJECTED`.

### 10.3. Входы, отдельные базы PnL и идентичность бота

Обязательный снимок **R3/T02 целого счёта**, T03 текущих позиций, T04 **всех** IN/OUT/SL/TP и других ботов, входы 05.1–05.4 (валюта/Mark/scope, исполненные и условные ордера, IM/MM/ликвидация, активы collateral), подтверждённое **E0=current Equity всего фьючерсного счёта** в одной оценочной валюте. Порог `L_limit=0.05×E0` проверяется **по каждому боту отдельно** и **всему набору сценариев**, без изменения исходного лимита и без использования виртуально выделенного «кошелька» Cross как обеспечения.

**Дополнительно для FR-030**: `bot_alias, strategy_version, inception/current_mark`, все фактические fill id, side, qty в base, fill price и timestamp, allocation к боту и positionIdx, уже реализованный PnL текущего жизненного цикла бота, ранее уплаченные fee/funding, текущая принадлежащая боту позиция/частичный close, все future IN/OUT, SL triggerBy / triggerPrice / orderType / limitPrice / reduceOnly / closeOnTrigger, возможные лаги и ограничения ликвидности, фактический параметр fee, funding rate c периодом, горизонт удержания, тип маржи и состояние AMR. **Без подтверждения причинной принадлежности исполнений боту нельзя суммировать или вычитать общий PnL позиции как PnL бота.**

**Две временные базы — нельзя смешивать:**
- `L_from_now`: **дополнительное ухудшение Equity от текущего Mark/позиционного состояния после T02**, включая оставшиеся обязательства, изменение UPL от текущего значения, новые fees/funding и позиционные/аккаунтные расходы в рассматриваемой ветви. **Не вычитать заново** из текущего E0 прошлые реализованные потери или комиссии, уже включённые в Equity.
- `L_lifecycle`: **чистый убыток всего жизненного цикла** бота: проверенные связанные уже реализованные PnL + текущий UPL + будущие закрытия/fees/funding, со ссылкой на **H01/историю связи исполнений**. Не создавать историю по названию монеты; убыток другой стратегии не автоматически убыток этого бота, прибыль другой позиции не гарантированная компенсация.

Пользовательский лимит FR-030 применяется консервативно к полному совокупному риску одного бота; **показывать обе базы**, если бот уже открыт, а не выдавать меньшее `L_from_now` за весь `L_lifecycle`. Если история необходима для конкретного заявления о всём боте, H01 требуется для **этого** утверждения, однако H02/H03 истории **Equity** не становятся обязательными и остаются `NOT_CHECKED` при их отсутствии (RV-01). Нельзя задвоить прошлые fee/funding между H01, realized PnL, current Equity и закрытой сделкой.

### 10.4. Уравнение чистого результата и сценарное дерево

Для *полностью исполненной и корректно сопоставленной связанной серии* **прямых linear USDT** позиций, в которой покупки/продажи формируют замкнутый круг, определить:

\[
PnL_{\rm net}(\omega)=PnL_{\rm realized\,price}(\omega)+PnL_{\rm open\,mark/exit}(\omega)
-\sum fee_{\rm charged}(\omega)+\sum funding_{\rm signed}(\omega)
-\sum other_{\rm explicit\,cost}(\omega).
\]

Здесь `funding_signed>0` — фактическое **поступление** (доход), `funding_signed<0` — выплата; если агрегатный `realizedPnL` Bybit **уже учитывает fees/funding**, повторно их **не вычитать**. Для отдельной позиции с однородными fill-лотами прямого контракта:
- **Long**, закрытый объём лота `q_i`: `pricePnL_i = q_i × (Pexit_i − Pentry_i)`.
- **Short**: `pricePnL_i = q_i × (Pentry_i − Pexit_i)`.
- **Частичные закрытия / перезаход / разворот:** вести FIFO/average cost **только согласно подтверждённому правилу учёта серии**, не считать один sell одновременно закрытием Long и новым Short на весь qty.
- Для нереализованного остатка текущий UPL **по Mark** для стресс-анализа, а фактическая комиссия выхода/цена исполнения — **отдельная величина**; Bybit может по умолчанию показывать UPL по Last (см. официальный P&L FAQ).

`L_scenario(ω)=max(0,−PnL_net(ω))` для базы **всей серии** либо `max(0, Equity_bot_now_reference − Equity_bot_after_ω)` для корректного **инкрементального** учёта, без перекрёстного зачёта двух баз. Не следует механически добавлять `margin_at_risk` к этой сумме — начальная маржа **не отдельный расход** поверх ценового убытка; при ликвидации риск фактической потери выделенной маржи пересчитывать по отдельной проверенной процедуре, **а не прибавлять к PnL снова**.

Для каждого возможного пути `ω` моделировать:
1. Будущие IN, частичные fill, открывающие/уменьшающие OUT, Hedge/One-Way, общие позиции разных ботов и новые уровни, **без двойного счета** по `orderId`.
2. Переключение risk tier/величины маржи, состояние Cross MMR либо Isolated LP; **ликвидация может начаться раньше SL**; изменения после T02 инвалидируют вход.
3. Триггер Stop (`Last/Mark/Index`) отдельно от **рыночной цены исполнения**; Market/IOC может закрыться частично, Limit может остаться полностью открытым; оставшаяся позиция участвует в дальнейшей ветви, включая ликвидацию.
4. Funding до выбранного горизонта **с фактическим или консервативно ограниченным интервалом**, комиссии открытия и закрытия, maker/taker **по реальному пути**, проскальзывание в **фактической** цене исполнения (не вычитать второй раз отдельным буфером, если оно уже отражено в `Pexit`), FX и haircut.
5. Максимум `L_scenario` по **подтверждённому охвату Ω**, включая совместные цены всех портфельных позиций, если Cross. FR-034 резерв всей сетки и FR-029 margin load проверяются **отдельно**, не вместо FR-030.

**Предотвращение double count:** для позиции с текущим UPL уже включённым в Equity, при расчёте инкрементальной потери `PnL_after−PnL_at_current_Mark`; при полном `L_lifecycle` использовать исторические открывающие/закрывающие события один раз. `InitialMargin` учитывается для достаточности обеспечения, а не как ещё одна торговая комиссия. В `PnL_net` и fee/funding отдельно применять либо **разложение по компонентам**, либо **готовый учтённый биржей clean realizedPnL**, не оба.

### 10.5. Что является доказуемым пределом, а что нет (RV-03)

**Short без жёстко обеспеченного ограничения выхода:** для `q_short>0` и неограниченной сверху цены исполнения `P_exit→+∞`, `L_price=q_short×(P_exit−Entry)→+∞`. Поэтому **один обычный Stop Market / Stop Limit**, даже при заранее установленной цене триггера и условном «2% slippage», **не** доказывает конечный максимум убытка. `stop-limit` обеспечивает **предельную цену только для фактически исполненной части**, но может вообще не закрыть позицию; незакрытый остаток остаётся потенциально неограниченным. `slippageTolerance`/IOC может также оставить незакрытый остаток; нельзя подменять риск **неисполнения** риском **исполнения по лимиту**.

**Long:** при предпосылке `P_exit≥0` и **конечном подтверждённом объёме** можно получить верхний предел **валового ценового** убытка от входа до цены 0: `Σ q_i×Entry_i` для фактически/условно набранной позиции. Но это **не** автоматически верхняя граница *чистого* убытка: funding при неограниченном времени, дополнительные комиссии, маржинальные события, новые IN, ликвидация, списания и неучтённый PnL серии способны увеличить сумму. Не переносить такую валовую границу на Short.

**Isolated:** биржевые условия могут ограничивать объём *фактически выделенного* обеспечения для конкретной изолированной позиции при ликвидации (см. [Bankruptcy Price](https://www.bybit.com/en/help-center/article/Bankruptcy-Price-Perpetual-and-Expiry-Contracts) и [Insurance Fund](https://www.bybit.com/en/help-center/article/Insurance-Fund)). Однако **не объявлять** плановую «маржу бота» гарантированным потолком чистого `L_lifecycle`: AMR, ручные пополнения, funding, fees, будущие IN, Hedge-слоты, отдельные открытые позиции и учет событий могут увеличить фактическую сумму. Нужна **явная проверка правил аккаунта, максимально допускаемого выделения средств и цепочки ликвидации** до заявления bound. **Cross:** весь общий Equity может использоваться для поддержки; «депозит/резерв бота» не изолирован, поэтому нет подтверждённого денежного cap по объявленному бюджету.

**Доказуемый предел FR-030 только при наличии:**
- точно определённого `Ω` и доказуемой **верхней** границы будущих Qty, фактической цены **полного** закрытия (или применимой биржевой границы списания для всего бота), комиссий, funding **в ограниченном горизонте** и других конкурирующих обязательств;
- доказанной связи бота с позициями и фактически применимого защитного механизма (включая отказ, частичное исполнение, ликвидацию до SL);
- проверенного сценарного максимума `L_upper≤0.05 E0` в **одной валюте** и на **всех существенных достижимых ветвях** вместе с требованиями к портфелю из 05.2/05.4.

**Если таких гарантий нет — `NOT_PROVABLE/UNVERIFIED` для FR-030, а не `PASSED`.** Предварительные расчёты частных стрессов могут дать полезный диапазон, но не конечную upper bound. При наличии **подтверждённого** обязательного нарушения (например, уже достигнутый лимит, подтверждённое исполнение/известный риск-предел ниже фактического убытка) → `REJECTED` независимо от недостающих других полей. Если заданный стресс превышает 5%, отметить `FAILED_UNDER_SCENARIO` и запретить представлять конфигурацию безопасной в заявленном стресс-наборе; **статус REJECTED** следует из него только при согласованной нормативной обязательности и применимости этого стресса/доказанного лимита, а не из произвольной выдуманной котировки.

### 10.6. Порядок действий агента

1. Определить `E0=current Equity` всего портфеля, единую валюту (USD↔USDT только с проверенной конверсией), `L_limit=E0×0.05`, бот/режим и источник данных; при R3 получить новый полный T02 и актуальную Mark.
2. Сверить принадлежность всех исполнений H01/T03/T04 боту, частичные закрытия и уже учтённые комиссии. Отдельно представить `L_from_now` и `L_lifecycle` при активной серии; недостаток H01 блокирует только заявления, для которых она нужна.
3. Создать ветви: до любых IN, после каждого из полной сетки, после одновременных IN других ботов, trigger/no-trigger, stop-market/stop-limit, partial/no-fill, price gap, ликвидация до SL, funding до горизонта, Cross совместные шоки. Для неизвестной версии формы платформы — не объявлять доступные свойства Stop/OCO.
4. Посчитать `PnL_net` по фактическим/явно предположенным fill prices и **отдельно** комиссионную/funding составляющую, не удваивая slippage и маржу.
5. Найти максимум по заданным сценариям и ответить, есть ли **доказуемая** верхняя граница по *всем* требуемым состояниям; показать `L_upper/E0` или `UNVERIFIED` с точной причиной.
6. Применить строгие статусы `REJECTED / UNVERIFIED / NEEDS_DATA / READY` по сквозному приоритету, указать FR-030 и другие известные нарушения; «синтетическая чистая прибыль при SL» не означает безопасность бота.
7. При непроверенном Cross (RV-02), loss bound (RV-03), P01/P02 или стрессах FR-038 **не** подтверждать полный `READY`.

## 11. Синтетические эталоны и границы проверки шага 05.5

### 11.1. Примеры (все числа вымышленные, без реальных котировок)

**SYN-LOSS-A — Short с полной сеткой и исполнением хуже Stop.** `E0=1000 USDT` (в этом тесте Equity уже в USDT), предел `50 USDT`. Short-IN1 `q1=1` по 100, Short-IN2 `q2=1` по 105; обе действительно исполнены. Триггер SL по 110 **не равен** цене исполнения, сценарное полное закрытие Buy по **112**; ставка fee **синтетически** 0.001 на входе и выходе, funding **синтетически выплачен** 1.40 USDT за заданный срок. Ценовой убыток `(112−100)+(112−105)=19`, fees `(100+105)×.001+224×.001=0.429`, funding `1.4`; **чистый убыток 20.829 USDT = 2.0829% E0**. Это **только один сценарий**, не max loss.

**SYN-LOSS-B — тот же Stop, исполнение по самому триггеру 110:** ценовой убыток `(110−100)+(110−105)=15`; fees `.205+.220=.425`, funding `1.4`; **16.825 USDT**. Разница с A `4.004 USDT` включает **и худшую цену закрытия, и дополнительную комиссию**. Не прибавлять «2 USDT проскальзывания ×2» вторично к числу A.

**SYN-LOSS-C — гэп и ущерб более 5%:** если тот же синтетический Short исполняется только по `140`, ценовой убыток `(140−100)+(140−105)=75`, комиссии `.205+.280=.485`, funding `1.4`, итог **76.885 USDT = 7.6885% E0**. Такой сценарий показывает **недоказанность** 5%-ного ограничения по одному Stop 110. При подтверждённой обязательности и достижимости такого сценария — нарушение допустимого сценарного набора; при произвольной выдуманной стресс-цене это **не утверждение реального REJECTED для BTC/ETH**.

**SYN-LOSS-D — ограниченная искусственная цена полного выхода:** если независимо **доказано** для *всех* ветвей, что полный Buy на этом объёме произойдёт **не хуже 122**, fees/funding ограничены приведёнными ставками/горизонтом, то `L_upper = (122−100)+(122−105)+0.205+0.244+1.40 = 40.849 USDT = 4.0849% E0`. Это **арифметический bound внутри искусственно ограниченного Ω**, **не биржевая гарантия** и не допустимый аргумент «стоп выставлен на 110».

**SYN-LOSS-E — Stop-Limit: не исполнено 50%.** После активации на 110 исполнен **только 1 BTC из 2 по 112**, второй BTC **остаётся в Short**. Даже если средняя стоимость частично закрытого объёма определена, нельзя посчитать итог полной серии как `20.829/2` либо считать остаток закрытым. При росте цены до 140 второй контракт продолжает нести убыток; `L_upper` без ограничения полного закрытия **не доказан**.

**SYN-LOSS-F — Long и нижняя граница цены:** полная вымышленная Long-сетка q1=1 по 100 и q2=1 по 105, Pexit=90, fee=.001 на обе стороны, funding outflow=1.4: цена дала убыток `(100−90)+(105−90)=25`, комиссии `.205+.180=.385`, total **26.785 USDT**. Худшая **валовая ценовая** потеря для этих двух фиксированных Long при гипотетической цене 0 — `100+105=205 USDT`; **205 не верхний предел нетто-убытка**, если funding/fees/маржинальные расходы не ограничены.

### 11.2. Нормативная матрица U01–U30 (ожидаемое поведение, не независимые вызовы LLM)

| ID | Вход/условие | Ожидаемое поведение |

### 12.2. Матрица совместной направленной нагрузки и корреляции (FR-025/037)

**Текущая линейная локальная чувствительность** в единой оценочной валюте, когда контракт и курс подтверждены:

\[
\Delta UPL_i \approx signedQty_i\;(Mark_{i,s}-Mark_{i,0})\;FX_{quote\to C}.
\]

Это выражение **точно** для прямого linear-номинала на фиксированном q и неизменном FX, но становится только *локальной* приближённой оценкой при IN/OUT, FX, fees/funding, risk tiers, нелинейном collateral или смене режима. Показать **gross** и **net directional** экспозицию отдельно: противоположные Hedge-слоты не удаляются из маржинальных обязательств, а Long BTC и Short ETH могут **терять одновременно** при BTC↓ и ETH↑.

**Корреляция:** вычислять `r_i,t=ln(Mark_i,t/Mark_i,t-1)` или простые доходности (`P_t/P_t-1−1`) **последовательно одним явно объявленным способом**, по **одинаковой категории и ценовому базису**: Mark-price Bybit linear, одна частота, интервал и UTC-таймстемпы, синхронные закрытые свечи. `corr_ij = cov(r_i,r_j)/(σ_i σ_j)` (выборочная ковариация/std с делением на `n−1`). Указывать `n, window, interval, lag, method`, долю пропусков, наличие нестандартных/делистинговых периодов и источник. Корреляция **не** требует принудительно учитывать стоимость разных токенов как если они были одной и той же денежной единицей.

**Минимум качества для заявленной числовой оценки по политике 05.6**: не менее **30 синхронных завершённых наблюдений доходности** после согласованной временной сетки, σ обоих рядов >0, явно проверенный процент пропусков и неизменность смысла категории/Mark; 30 — **технический порог качества MVP, а не биржевая гарантия или статистическая достаточность**. Для устойчивости сравнивать короткое и длинное окно при достаточных данных, отдельно направленные **совместные негативные** хвосты. Менее 30 наблюдений, константный ряд или несопоставимые таймфреймы → `CORRELATION_UNVERIFIED`, **не** подставлять `ρ=0`. Даже `ρ≈−1` на истории не гарантирует страховки в будущем и **не отменяет** обязательный совместный стресс.

Матрица итогов: `symbol/slot/bot, side, quote/collateral, Mark, gross notional, signed delta per 1% Mark, order/grid exposure, conditional future direction, pairwise ρ with quality, co-loss modes, worst joint branches`. При отсутствии истории всё ещё выполнить консервативный сценарный **co-loss map** на подтверждённых текущих позициях, но **не заявлять, что эмпирическая корреляция рассчитана**.

**Источники:** [Bybit V5 Mark Price Kline](https://bybit-exchange.github.io/docs/v5/market/mark-kline) даёт датированные Mark-свечи `startTime (Unix ms), open/high/low/close`, возвращаемые в **обратной хронологии**, по категориям и интервалам. [Обычная Kline](https://bybit-exchange.github.io/docs/v5/market/kline) — **торговая**, не Mark: её нельзя без явной трансформации и обозначения подменять исторической Mark для ликвидационной/портфельной оценки. В Mark-свечах **нет объёма и реального порядка внутрисвечных исполнений**; OHLC сам по себе не доказывает, в каком порядке цена затронула SL и IN. История запрошена только как открытая спецификация; **никаких рыночных цен в этом шаге не получали**.

### 12.4. Протокол F — фиксированные шоки

Минимальная матрица: по **каждому** действующему и потенциально открывающему активу `±5%, ±10%, ±15%, ±30%` от согласованной текущей Mark, отдельные шоки и **совместные co-loss** шоки Long↓/Short↑ с несколькими символами. Это **пороговая проектная сетка MVP**, а не эмпирический квантиль/лимит риска. По потребности расширять шоки, не уменьшать ради прохождения лимитов. Помимо Mark стрессовать FX/collateral и доступность рынков/ликвидности — заданными явно величинами/режимами, не подразумевая `USD=USDT` на реальном счёте.

**F-SYN, искусственный одновалютный портфель:** E0=1000 USDT, BTCUSDT Long `q=2, entry=Mark100`, ETHUSDT Short `q=3, entry=Mark50`. При BTC−10% (`90`) и ETH+20% (`60`): `ΔUPL=2×(90−100)−3×(60−50)=−20−30=−50`. **Только** в этом синтетическом сценарии дополнительные итоговые fees=2 и funding expense=1, так что `E_s=1000−50−3=947`, `loss=53` (5.3% E0). Это **общий портфельный loss**, не автоматически убыток одного бота.

**F-SYN-grid:** отдельные условные IN при пересечении BTC=95 (Long +1) и ETH=55 (Short +1) с **явно предполагаемым полным исполнением именно по 95/55**; в конечных Mark BTC90/ETH60 новые позиции дают дополнительно `−5−5=−10`, суммарный портфельный UPL change `−60`, те же заданные totals costs=3 → `E_s=937`, `loss=63`. ### 12.5. Протокол A — адаптивные шоки (волатильность и режим)

Для каждого актива вычислить `σ_i` на сопоставимых Mark-доходностях одного интервала (например, sample std, `n≥30` для допустимого пользовательского вывода), задать `horizon_bars` и `k>0` как **явные параметры**, а не скрытую вероятностную гарантию.

Простая документальная базовая схема:
\[
a_i=\max(floor_i,\;k\sigma_i\sqrt{horizon\_bars},\;gap\_proxy_i)
\]
где `floor_i` — минимум из фиксированного протокола, `gap_proxy_i` — консервативная проверенная оценка гэпа. Если `gap_proxy_i` неизвестен, **не** присваивать ему молча 0: стресс можно показать условно с допущением, но полноценное доказательство максимального убытка не получено. Увеличивать `k/floor` для режима повышенной волатильности или нестабильной ликвидности по объявленной политике; никогда не уменьшать `a_i` потому, что данные старые. Если доступна только Price/OHLC без надёжной ликвидности — модель исполнения `UNVERIFIED`.

**A-SYN:** вымышленные три доходности BTC `[−2%,0,+2%]`, ETH `[−4%,0,+4%]` дают sample `σ_BTC=2%`, `σ_ETH=4%`. При `k=3, horizon=1, floor=5%` и условном `gap_proxy≤floor` получается `a_BTC=6%`, `a_ETH=12%`. Для Long BTC100→94 и Short ETH50→56: старые позиции теряют `12+18=30`. Если **условно** исполняются сетки q+1 при 95/55, добавляется `1+1=2`, общая потеря цены `32` и синтетические costs3 → `35 USDT`. **Три доходности недостаточны для вывода о реальной текущей волатильности**: статус синтетического опыта `MATH_ONLY / INSUFFICIENT_SAMPLE`, а не готовность рыночной оценки.

Нельзя из отсутствия рыночной истории объявить исторический стресс `PASS` или заменить его синтетикой без явного отличия и нового согласованного решения о критерии готовности.

### 12.7. Протокол R — обратный стресс (reverse)

Выбрать **конкретное нарушение**: например, `L_bot/E0>5%`, `IM_s/E0>30%`, `AccountMMR≥100%`, недостача покрытия сетки, нарушенная дистанция FR-032 или `≤0` доступного обеспечения. Найти **первую границу** по **определённым** параметризованным путям `γ(t)`, `t≥0`, и отдельным разрешённым событиям исполнения: `t* = inf{ t: limit(γ(t)) нарушен/достигнут }`; различать **точку равенства нормативному пределу** и **первый шаг строгого превышения**. Если разные ограничения нарушаются раньше — сообщать **первое установленное событие**, а если Cross/Short model не проверена, **первое полное событие UNVERIFIED**.

**R-SYN, учебная модель из F:** `BTC(t)=100−10t`, `ETH(t)=50+10t`, `0≤t≤1`; BTC Long2, ETH Short3, E0=1000, условные IN BTC Long1 при 95 и ETH Short1 при 55 (оба при `t=0.5`, fill exactly by assumption). Заданы **фиксированные суммарные новые fees+funding=3 USDT при t≥0.5**. После двух исполнений:
\[
L_{\mathrm{portfolio}}(t)= 50t + (10t-5) + (10t-5) + 3=70t-7,\quad t\in[0.5,1].
\]
На границе условной **5%-ной портфельной потери** `L=50` получаем `t=57/70≈0.8142857143`, BTC≈91.85714286 (−8.142857%), ETH≈58.14285714 (+16.285714%). Сразу при `t>57/70` эта **условная портфельная** потеря превышает 5%. **Но FR-030 — лимит убытка ОДНОГО бота, а не портфеля:** нельзя объявить его нарушенным, пока не установлен bot attribution. Если оба IN и позиции принадлежат одному боту в явно заданной искусственной модели, тогда это был бы тест FR-030 для него; в реальном Cross без RV-02/03 это не доказательство реального первого лимита.

**R-SYN-backward:** при одинаковом конечном BTC=90/ETH=60 портфельный синтетический убыток с обоими fill `63`, без дополнительных fill `53`. Если из-за гэпа один IN не исполняется, **другая ветвь** меняет границу; нельзя считать сценарий исполнения универсальным.

**Запрет:** обратный поиск на ограниченном выбранном `γ` **не** доказывает глобально наиболее опасную комбинацию; корреляция на истории не доказывает вероятность `γ`. Отдельно отмечать чувствительность к order fill, FX, fees, liquidity и risk tiers. Число `t*` не является гарантированной ценой принудительного закрытия Cross/Short.

## 14. Исторические лимиты Equity, дневной риск и блокировки (шаг 05.7)

> **Статус 05.7: `COMPLETED / APPROVED` (15.10.2026)** ([акт](risk-05-07-validation.md#6-формальная-приёмка-шага-057--15102026)). Текст определяет **условные исторические проверки** FR-028/035, обязательное соблюдение известных запретов FR-036 и интеграцию с итоговым решением FR-039/040/050/052. Это **не** фактическая история счёта, не выполненный на реальных данных расчёт просадки и не самостоятельное право на `READY`. **05.8 впоследствии документально реализован и ожидает приёмки**; RV-02, RV-03, TV-01–TV-04 сохраняются.

### 14.1. Разные уровни обязательности H01–H04

- **H01 / T05:** история **связанной серии бота** для корректного `L_lifecycle`, чистого PnL и сценария восстановления потерь. Может быть обязательной **для конкретного утверждения о серии**; не подменяется историей общего Equity.
- **H02 / T06 (исторический Equity):** условная проверка **15%-ной** просадки от скорректированного high-water mark (FR-028). Отсутствие полной достоверной истории → `NOT_CHECKED`, не `REJECTED` и **не автоматический запрет READY**, если все **обязательные текущие** проверки удовлетворены.
- **H03 / T06 (дневной Equity):** условная проверка **3%-ного** дневного убытка от скорректированной дневной базы, старт **00:00 Europe/Moscow**, с реализованным и нереализованным PnL без двойного счёта (FR-035). Нет достоверного начала/потоков → `NOT_CHECKED` и перечисление пробела, не выдуманное значение.
- **H04 / T06 или иной допустимый датированный источник:** **уже достоверно известное нарушение и состояние его блокировки**. При подтверждённом активном H04 агент **обязан** запретить новое увеличение риска по FR-036, **даже если H02/H03 текущего запроса отсутствуют**, пока не подтверждены условия разблокировки. H04 не становится несуществующим из-за смены чата, отсутствия T06 или пополнения счёта.

**Разные понятия:** история **ценовых Mark** для фактически выполненного исторического стресс-теста 05.6 **не равна** истории **Equity счёта H02/H03**. Первую нельзя выдумать ради выполнения FR-038; отсутствие второй — согласованная условная неполнота RV-01. `NOT_CHECKED` — локальная метка, **не пятый торговый статус**.

### 14.2. Достоверный ряд, единицы и внешние денежные потоки

**Исторический снимок** `h_i=(observed_at_UTC, account_scope, E_i, currency_C, source, type, completeness)`. Дополнительно нужны `external_flow_j=(booked_at_UTC, amount_C_signed, origin, confirmed)` и события смены обеспечительного контура, переоценки залога, долга, комиссий, funding, открытых позиций. `E_i` — именно **Equity всего выбранного согласованного account scope**, не Wallet Balance, PnL одного бота, available balance или суммарный номинал.

**Валюта:** все `E_i` и `flow_j` приводить к **одной подтверждённой оценочной валюте** с документированными историческими FX/haircuts/моментами конверсии; запрещено трактовать USD как USDT без конверсии. Вклад/вывод в валюте залога, заём, внутренний перевод между субсчетами/обеспечительными контурами классифицировать по `account_scope` и **изменению внешнего капитала**, а не исключительно по полю `wallet_transfer`. Перемещение между двумя учитываемыми активами **одного** scope — не внешний поток, если итоговая стоимость капитала не изменилась; перевод между разными scope требует отдельного учёта, а не искусственной прибыли/убытка.

**Полнота и качество:** состояние на начале истории/суток, **хронологически возрастающие** и неповторяющиеся наблюдения, исторические cash-flow события в промежутках, все известные исходящие/входящие капиталовложения. Пропущенные значимые интервалы/непроверенная оценка обеспечения **не доказывают исторический максимум/дневную базу**, даже если две крайние точки выглядят безопасно. Для H02, H03, H04 указывать `coverage_start/end, sampling_frequency, gaps, source/provenance, FX, monetary_basis, last_checked_at`, статус `VERIFIED/NOT_CHECKED/CONFLICT`. Если часть проверенных точек **уже доказывает нарушение** на согласованной базе, неизвестные старые пики **не должны скрывать** известную блокировку; утверждать отсутствие нарушений по неполной серии нельзя.

**Переоценка:** `ΔE` уже включает реализованный/нереализованный PnL, комиссии и funding с учётом актуальной биржевой семантики; **не вычитать** их второй раз. Проверять `ΔE = ΔrealizedPnL + ΔunrealizedPnL − new_fees + signed_funding + collateral_FX_PnL + net_external_flow + verified_other_changes` **только если** компоненты не входят друг в друга. Невязка без объяснения → `UNVERIFIED` для доказательства конкретной истории, а не выбор удобной цифры.

### 14.3. High-water mark с поправкой на внешние потоки (H02)

Для **проверенного** хронологического ряда с текущей оценочной валютой C:
1. На старте `H_0=E_0>0`. `H_i` — максимум капитала **с поправкой на внешние денежные потоки** на момент `i`.
2. Для наблюдения `i` с накопленным **знаковым внешним** потоком `F_i` **с прошлого обработанного наблюдения** (пополнения положительны, выводы отрицательны) скорректировать прежний пик `H_i^pre=H_{i−1}+F_i`; далее `H_i=max(E_i, H_i^pre)`. **Критически:** нельзя применять один и тот же внешний поток дважды, добавлять к HWM прибыль от рыночной переоценки как внешний поток либо вычитать вывод как торговый убыток. Разбиение на мгновения cash-flow отдельно даёт более точный след; если между событиями лежит неподтверждённый ценовой пик, безопасный `H_i` не доказан.
3. `DD_i=(H_i−E_i)/H_i×100%`, `DD_max=max_i DD_i`, только если `H_i>0` и вся существенная последовательность достоверна. **Порог блокировки: `DD_i≥15%` или ранее подтверждённый действующий H04**, не только `>15%` — FR-036 описывает **достижение** предела. При `H_i≤0`/некорректной валюте расчёт `UNVERIFIED`.
4. События `deposit/withdrawal` могут механически изменять **процент** просадки через знаменатель; они **не снимают действующий H04** без подтверждённых условий. **Пополнение не является доказательством восстановления торгового результата**, и историческая серия не «перезапускается» произвольно после просадки.

**Область/неоднозначность:** приведённая формула — **выбранная MVP-политика оценки flow-adjusted HWM**, а не универсальная биржевая норма или полноценный time-weighted return расчёт. Времена cash-flow должны быть валидированы; при существенных сложных преобразованиях обеспечения или неизвестном промежуточном пике → `NOT_CHECKED/UNVERIFIED`, не ложный PASS. Для заявления о **максимальной** просадке нужна достаточная плотность/полнота исторических наблюдений или допустимая доказанная верхняя граница; две точки не доказывают отсутствие промежуточной просадки.

### 14.4. Дневной лимит 3% — московская дата и консервативная база H03

**Торговые сутки пользователя:** локальный интервал `[00:00, 00:00 следующих суток)` в **Europe/Moscow (UTC+3)**. Достоверные события и Equity хранить как абсолютные UTC/offset, **пересчитывать в московскую дату**, не считать UTC-день «торговыми сутками». Например, `2026-10-14T21:00:00Z = 2026-10-15 00:00 МСК`. Equity **ровно на начале локальных суток**, либо подтверждённая воспроизводимая ledger-реконструкция — обязательны **только для утверждения о фактически проверенном H03**, но их отсутствие **не блокирует READY само по себе**.

Обозначим `B0=Equity[local_day_start]>0`, `F_day(t)=Σ confirmed external_flow_C` от начала локальных суток **до момента t включительно**, `E_t=current Equity_C`. **Потеря торгового результата с поправкой на потоки**:
\[
PnL_{\mathrm{day,adj}}(t)=E_t-B_0-F_{\mathrm{day}}(t).
\]
Это **чистое ухудшение Equity**, уже включающее реализованный и нереализованный PnL, комиссии и funding. Нельзя прибавлять `realizedPnL` к `E_t` и вычитать `UPL` ещё раз, если они уже в Equity.

**Консервативная проектная база (требует утверждения как часть шага 05.7):**
\[
B_{\mathrm{day}}(t)=\min \{B_0,\;B_0+F_{\mathrm{day}}(t)\},\quad B_{\mathrm{day}}(t)>0.
\]
Положительный перевод **не повышает внутридневной порог убытка задним числом**, а вывод уменьшает капитал, относительно которого агент разрешает новое увеличение риска. **Это намеренно более строгая политика MVP**, чем простое сравнение с `B0+F_day` при пополнении, и **не формула биржи Bybit**. По окончании суток новая подтверждённая начальная база считается для следующего дня. Если скорректированная база неположительна/потоки неполны → не доказывать лимит, анализировать текущее критическое обеспечение отдельно.

\[
DailyLossRate(t)=\frac{\max(0,-PnL_{\mathrm{day,adj}}(t))}{B_{\mathrm{day}}(t)}\times100\%.
\]

**Блокировка:** подтверждённое `DailyLossRate≥3%` **достигает** дневного лимита FR-035/036, поэтому **нельзя** разрешать новый риск; ровно 3% — **ограничение уже достигнуто**. Дневные убытки за предыдущие сутки не складываются с новой базой без отдельной H04-блокировки; **переход в 00:00 не уничтожает действующий исторический запрет**. Если дневная база/потоки отсутствуют → H03 `NOT_CHECKED`, **без** фиктивного «3% не превышено».

**Нужная полнота:** отсутствие свечи/снимка в 00:00 **не разрешает молча интерполировать** значение — допускается только подтверждённая ledger-реконструкция (баланс+переоценка на границе с проверенными ценами/валютами/позициями) и явная запись метода. При известном нарушении H04, даже когда сегодня B0 не восстановлена, H04 действует до подтверждённой разблокировки.

### 14.5. Состояние блокировок H04: события, снятие и приоритет

Хранить **датированный журнал решений**, не выдумывать продолжительное наблюдение. Поля: `breach_id, source, verified_at, triggered_at_UTC, local_trading_day, kind=DAILY_3/HWM_15/OTHER, threshold, verified_value, currency/scope, blocker_status, reset_eligible_at, unlock_conditions, manual_user_confirmation, last_rechecked_at, reason`. Не помещать реальные выписки, UID, идентификаторы/ключи API в публичный GitHub; реальная история остаётся у пользователя или в безопасном разрешённом подключении.

**D — дневная блокировка:** после подтверждённого **достижения ≥3%** она действует **до следующего 00:00 Europe/Moscow и нормализации риска**, обе части обязательны. После полуночи нельзя автоматически отметить `UNLOCKED` без **нового полного T02**, проверки текущих рисков/блокировок и подтверждения, что условия нормализации действительно выполнены. Если дата перешла, но T02/условия неизвестны → `ACTIVE_OR_UNVERIFIED_UNLOCK`, не `READY`.

**H — историческая блокировка:** после подтверждённой **просадки ≥15%** требуется **нормализация риска и отдельное явное подтверждение пользователя** для снятия исторической блокировки. Пополнение, восстановление Equity либо очередное 00:00 **не** заменяют явного подтверждения. Подтверждение пользователя не отменяет действующие жёсткие лимиты (например, при MM критическом); если нормализация не доказана, запрет сохраняется. **Не генерировать фиктивный факт подтверждения**. Хранить хотя бы факт/время/область согласования в допустимом для проекта журнале, не сведения счёта.

**Несколько блокировок:** дневной запрет может закончиться раньше исторического, но суммарное решение остаётся заблокированным, пока существует **хотя бы одна действующая** причина. Достоверный `FR-029/030/032` провал одновременно с H04 тоже не снимается ни одной исторической разблокировкой.

**FR-039: уменьшение риска** (закрытие/сокращение, отмена открывающих IN, снижение плеча/номинала согласно фактически допустимым правилам) **не запрещать** механическим `REJECTED` для нового риска. Сообщать действие как **отдельный risk-reduction путь** с его собственными требованиями безопасности и неизвестными последствиями; не обещать немедленное исполнение, не менять настройки и не торговать автономно. Условия H04 **не оправдывают усреднение** или открытие дополнительного хеджа без проверки роста совокупного риска.

### 14.6. Воспроизводимый алгоритм проверки H02/H03/H04

1. Определить действие `intent`: `INCREASE` (новая стратегия, новый IN, увеличение допустимого номинала), `REDUCE` (реальное снижение портфельного риска), `INFORMATION_ONLY`; считать «изменение параметра» потенциальным `INCREASE`, если изменяется будущая достижимая нагрузка.
2. Для `INCREASE` проверить **обязательные текущие** T02/T03/T04, AD-009/R3, FR-029/030/031/032/033/034/037/038, RV-02/RV-03, платформенные P01/P02. При **финальном** подтверждении обязательно запросить новый согласованный T02/Mark и сверить скриншот формы (FR-050/052); документ 05.7 **не** делает это автоматически.
3. Если достоверно известен **действующий H04**, запретить `INCREASE` (локально `BLOCK_ACTIVE` → торговый `REJECTED`), независимо от отсутствия H02/H03. Если есть подтверждённый новый `H02 DD≥15%` либо `H03 DailyLossRate≥3%`, зарегистрировать/применить соответствующую блокировку. **Недостаток других данных не скрывает уже доказанное нарушение.**
4. Если H02/H03 отсутствуют или не восстанавливаются надёжно, отметить **отдельно для каждого** `NOT_CHECKED`, не `PASSED` и **не** новый запрет. Если **есть** источник с противоречивыми числами, описать конфликт и невозможность проверить H02/H03; не приравнивать непроверенный источник к установленному нарушению.
5. Если подтверждена дата истечения дневного запрета и нормализация риска — можно записать закрытие **только дневной** блокировки. Историческую — только после нормализации и **прямого подтверждения пользователя**. Переход в 00:00, перевод на счёт и исчезновение H02 из последнего запроса **не** являются достаточными доказательствами снятия.
6. Свести причины в матрицу `15. `REJECTED` для нового риска при известном применимом жёстком нарушении; без него `UNVERIFIED` при непроверенной критичной модели/конфликте; `NEEDS_DATA` при отсутствующих обязательных текущих входах. H02/H03 `NOT_CHECKED` само по себе **не меняет** итог; локальное «прошло» 05.7 не даёт `READY` без остальных этапов.
7. Сохранить версию данных, явную область решения, перечень проверенных/непроверенных FR, активные блокировки, минимально необходимые запросы и рекомендации безопасного уменьшения риска. Не утверждать, что агент мониторит изменения между сообщениями.

### 15.1. Торговый статус и допустимое действие

| Достоверный результат | Локальные метки | Торговый итог для нового увеличения риска |
|---|---|---|

| Нет доказанного нарушения, **есть конфликт источников/неверифицируемая обязательная Cross/Short модель**, FX, tier | `UNVERIFIED` с областями | **`UNVERIFIED`**, не READY; запрос/уточнение модели |
| Нет доказанного нарушения, **отсутствует** обязательный текущий T02/Mark/ордер/комиссия/форма | `MISSING` | **`NEEDS_DATA`**, конкретный минимальный T02/T03/T04/P02 |

| Все применимые текущие проверки, рисковые модели, стресс, форма P02 и актуальность действительно доказаны, H04 нет | `PASSED_FOR_FULL_SCOPE`; H02/H03 `PASSED` или `NOT_CHECKED` | **`READY` допустим только в будущем после этапов 05.8/06 и реальной валидации**; текущее состояние проекта не соответствует |

**Порядок при одновременных причинах:** подтверждённый отказ `REJECTED` → существенная `UNVERIFIED` модель/конфликт → отсутствующие обязательные текущие входы `NEEDS_DATA`; все причины перечисляются. `NOT_CHECKED` не конкурирует с торговыми статусами и не означает отсутствие нарушения. **Если числовое нарушение зависит от недостоверного знаменателя/валюты, нельзя считать его доказанным** и назначать `REJECTED` произвольно.
